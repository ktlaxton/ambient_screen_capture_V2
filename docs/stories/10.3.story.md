# Story 10.3: Content Sources: Media Files & Mirror Real Monitors

## Status
Ready for Review

## Story
**As a** developer/QA,
**I want** to fill virtual monitors with a video/image file or a live mirror of a real physical
monitor, instead of only synthetic test patterns,
**so that** effects can be judged on realistic content — and so the one path that runs *real* WGC
capture through the simulator is exercised — on any fabricated monitor layout, on a 2-monitor machine.

## Context
Story 10.1 added `SimulatedScreenCaptureService : IScreenCaptureService` (the drop-in at
`App.xaml.cs:174`) that emits deterministic test-pattern BGRA at the source resolution, honoring the
capture contract: a tightly-packed, top-down, no-stride BGRA buffer that is **reused** per frame and
must be consumed synchronously by the subscriber
[Source: src/Engine/Capture/IScreenCaptureService.cs:26-35; src/Engine/Capture/ScreenCaptureService.cs:29-35].
Synthetic gradients prove the pipeline runs, but they make effects hard to evaluate by eye — edge
glow, aurora and audio-bars all look most convincing on real screen content.

This story extends the simulated capture source with two realistic content modes:

- **(A) Media file** — decode a video or image, scale/letterbox to the source `MonitorInfo`'s
  `Width × Height`, convert to tightly-packed BGRA, and loop on EOF.
- **(B) Mirror** — instantiate the **real** `ScreenCaptureService` internally for a chosen physical
  monitor (real WGC via `CaptureInterop.CreateItemForMonitor`, `ScreenCaptureService.cs:205`),
  subscribe to its `FrameCaptured`, and re-emit those BGRA frames as the simulator's source frame.
  This is the **only** place real screen capture runs inside the simulator.

It also wires **per-monitor content assignment** so each virtual monitor can be set to synthetic /
media / mirror-of-physical-N / blank. The minimal selector lives here; the full interactive editor is
10.5.

**Single-source reality (must be preserved, not "fixed"):** the engine captures exactly **one**
source monitor and every target projects from it
[Source: src/Engine/Services/EngineCoordinator.cs:320-321 (`ResolveSource`); :238 (`_capture.Start(source)`)].
So content only *drives the effect* on the source monitor. Content assigned to a non-source virtual
monitor is **visual context** for the composite (drawn as that viewport's background in 10.2) — it is
**not** fed into the effect. That matches real product behavior; document it as such, not as a bug.

This story depends on 10.1 (the `SimulatedScreenCaptureService` and the `SIMULATOR_ENABLED` +
`--simulator` gating) and is best *seen* with 10.2 (the composite window), but its plumbing and tests
do not require 10.2.

## Acceptance Criteria

1. **Media-file source.** A virtual monitor's source content can be set to an image (PNG/JPG/BMP) or a
   video (MP4/WebM). The decoder produces frames scaled/letterboxed/cropped to the source
   `MonitorInfo.Width × Height`, converted to **tightly-packed, top-down, 4-byte BGRA with no row
   padding** (the exact `ScreenFrameEventArgs` contract), and emitted on the configured cadence
   (`maxFps`, the same knob 10.1's synthetic source honors). A still image emits a steady repeated
   frame; a video plays and **loops seamlessly on EOF**. The decode/scale/letterbox math is a pure,
   unit-tested helper independent of the capture service and of any media library types.

2. **Mirror source.** A virtual monitor's source content can be set to "mirror physical monitor N".
   This instantiates the **real** `ScreenCaptureService` for that physical monitor's `MonitorInfo`
   (real WGC, `ScreenCaptureService.cs:205`), subscribes to its `FrameCaptured`, and re-emits those
   BGRA frames as the simulated source's frame — copied/rescaled to the *virtual* source resolution if
   the virtual monitor's resolution differs from the physical one. The re-emitted frame still honors
   the buffer-reuse + synchronous-consume contract downstream
   [Source: src/Engine/Processing/DataProcessingService.cs:264-266]. This is the single place real
   capture runs in the simulator; everywhere else stays synthetic/media.

3. **Per-monitor content assignment.** Each virtual monitor in the topology can be independently
   assigned one of: `synthetic` (pattern from 10.1), `media` (file path), `mirror` (physical monitor
   id), or `blank`. The assignment is carried in the JSON scenario fixture (per-monitor, optional;
   default = synthetic) and is settable from a minimal in-simulator selector. The frame format the
   source emits remains tightly-packed BGRA at the *source* monitor resolution regardless of content
   mode.

4. **Only the engine's single source drives the effect (documented).** The engine continues to capture
   exactly one source monitor; only that monitor's assigned content reaches the effect pipeline
   [Source: src/Engine/Services/EngineCoordinator.cs:320-321, :238]. Content assigned to non-source
   virtual monitors is visual context for the composite (10.2's viewport background) and is **not**
   processed. This is explicitly documented (in `SIMULATOR.md` stub / Dev Notes) as matching real
   product behavior, not a limitation to fix. No change to `EngineCoordinator`, `EdgeZoneExtractor`,
   the bridge, or the effect runtime.

5. **Content-source change without a full engine restart.** Switching a monitor's content mode (or the
   media file, or the mirrored physical monitor) takes effect on the running engine. A full
   `EngineCoordinator` teardown is **not** required; a `Stop()`/`Start()` of the simulated capture
   source (the established switch mechanism — `Start` already switches sources cleanly,
   `IScreenCaptureService.cs:14-15`) is acceptable. The effect keeps running; only the source content
   changes.

6. **Graceful failure — never throw (NFR5).** A missing/unreadable/undecodable media file, or an
   unavailable/disconnected/duplicate-of-source physical monitor for mirror, **never throws into the
   host**. Instead the source raises the `Error` event with `Source = "capture"` (the existing
   `PipelineErrorEventArgs` contract, `IScreenCaptureService.cs:37-43`) and falls back to a safe frame
   (blank or the synthetic pattern) so the pipeline keeps running. Mirror cleanly tears down the
   internal real `ScreenCaptureService` when switched away or on simulator shutdown (the real service's
   `Stop`/`Dispose` are idempotent and never throw, `ScreenCaptureService.cs:169-196`).

7. **Fidelity invariant.** All new code lives behind the capture seam (`IScreenCaptureService`) and the
   `SIMULATOR_ENABLED` + `--simulator` gate from 10.1. No fork of projection / effect / LED / audio
   logic; no bridge-contract change. The only "real engine" code reused for mirror is the unmodified
   production `ScreenCaptureService`. Release/Velopack build contains no simulator IL; zero Free/Premium
   impact.

8. **Tests green & extended.** xUnit covers: media decode → BGRA correctness (dimensions, tight pack,
   top-down order, letterbox bars where applicable) on a tiny fixture image; image loop/steady-frame;
   mirror passthrough (a fake `IScreenCaptureService` feeding the mirror adapter re-emits identical
   BGRA, honoring the reuse contract); missing-file fallback raises `Error` + safe frame, no throw;
   unavailable/duplicate-of-source physical monitor fallback raises `Error` + safe frame, no throw;
   content-mode switch on a running source. Existing xUnit + Vitest suites stay green.

## Dev Notes

### Fidelity invariant (state it plainly)
The simulator MUST reuse the real pipeline — `EngineCoordinator`, `MonitorLayout.ComputeRelation`,
`monitorProjection.ts`, the effect runtime, `LedProjection`, `AudioModulation` — **unmodified**. No
forking of projection/effect/LED/audio logic and **no bridge-contract change**. For this story the
adaptations allowed are: (1) the capture seam swap (10.1's `SimulatedScreenCaptureService`, the
`App.xaml.cs:174` drop-in) and (2) for mirror, reusing the *unmodified* production
`ScreenCaptureService` as an internal frame source. Canvas scaling (10.2) is the only rendering
adaptation. If mirror or media forces a `ScreenFrameEventArgs`/bridge change, that is out of scope —
keep the contract as-is.

### The capture contract (do not violate it)
[Source: src/Engine/Capture/IScreenCaptureService.cs:10-43]
- `IScreenCaptureService`: `Start(MonitorInfo)` (:15, switches source cleanly if already capturing),
  `Stop()` (:17), `FrameCaptured` (:20), `Error` (:23), `IsCapturing` (:12), `IDisposable` (:10).
- `ScreenFrameEventArgs` (:26-35): `PixelsBgra`, `Width`, `Height`, `TimestampMs`. Doc-comment (:26):
  *"a downscaled frame: tightly packed 32-bit BGRA, top-down rows, no padding."* Media + mirror output
  must match this exactly.
- `PipelineErrorEventArgs` (:37-43): `Source` is one of `"capture" | "audio" | "processing" |
  "hosting"` (:39). Use `"capture"` for all simulator content-source failures.

### Buffer-reuse + synchronous-consume contract (the crux of media/mirror)
[Source: src/Engine/Capture/ScreenCaptureService.cs:29-35 (remarks), :74 (`_pixelBuffer` reused),
:418-426 (raise outside lock while in-flight guard held)]
- The real service reuses a single `_pixelBuffer` per frame; the subscriber must copy synchronously.
  `DataProcessingService.OnFrameCaptured` honors this by copying immediately into `_latestPixels`
  [Source: src/Engine/Processing/DataProcessingService.cs:264-266], guarded by a malformed-frame check
  (:251-259: null buffer, non-positive dims, or `buffer.Length < Width*Height*4` are dropped). So:
  - The simulated source may also reuse one output buffer across frames — that is contract-correct.
  - **Mirror**: in the real service's `FrameCaptured` handler the BGRA you receive is the real service's
    reused buffer; copy/rescale it into the simulator's own output buffer **before** the handler
    returns, then raise the simulator's `FrameCaptured`. Do not stash the raw reference.

### Mirror: reuse the real ScreenCaptureService unmodified
[Source: src/Engine/Capture/ScreenCaptureService.cs:200-225, :205; src/Engine/Capture/Interop/CaptureInterop.cs:47-61]
- `StartLocked` calls `CaptureInterop.CreateItemForMonitor(monitor.HMonitor)` (:205) — real WGC, no
  picker. The mirror source constructs its **own** `new ScreenCaptureService(logger)` (NOT the DI
  singleton, which is the *simulated* service) and `Start`s it on the physical `MonitorInfo`.
- The real service auto-downscales to a ~64px mip (`TargetMipWidth`, :46) — fine: this is the same
  tiny analysis buffer the engine consumes anyway, and the simulator only needs enough fidelity to feed
  the effect / draw a background. Rescale to the virtual source resolution in `SimMediaScaler` if the
  composite wants a larger background; the effect itself only needs the edge zones the engine already
  extracts from the small frame.
- **Live `HMonitor`**: `MonitorInfo.HMonitor` is `[JsonIgnore]` and "only valid until the display
  configuration changes" [Source: src/Engine/Models/MonitorInfo.cs:22-24]. Fabricated 10.1 topologies
  carry a sentinel handle that must never reach WGC. For mirror you MUST resolve the *real* physical
  `MonitorInfo` (with a live handle) from the real `MonitorDetectionService.GetMonitors()`
  [Source: src/Engine/Services/MonitorDetectionService.cs:45-97, HMonitor set at :77] at switch time,
  and re-resolve if the real topology changes (`OnItemClosed` in the real service already raises `Error`
  on unplug, `ScreenCaptureService.cs:487-508` — forward it).
- Reject mirroring the physical display that hosts the simulator's own composite window (capture
  feedback loop) and reject a physical id not present in the real enumeration → `Error` + blank
  fallback.

### Media decode — pick the minimal-native-dep option
- **Images** (PNG/JPG/BMP): decode with WIC (`System.Windows.Media.Imaging.BitmapDecoder`, already
  available in WPF — no new dependency) or `System.Drawing.Common`. WIC is preferred (in-box for WPF,
  gives a `BitmapSource` you can `CopyPixels` into a `Bgra32` buffer directly). Convert to
  `PixelFormats.Bgra32` then `CopyPixels` → tight buffer, top-down (WIC is top-down by default).
- **Video** (MP4/WebM): the trade-off — a full ffmpeg/`OpenCvSharp` path adds native binaries and
  packaging weight for a dev-only tool. Prefer the lightest viable option in this order: (a) an
  **image-sequence** source (a folder of frames) — zero new native deps, fully deterministic, ideal for
  tests/automation; (b) a single representative still image (covers most "realistic content" needs);
  (c) one simple in-box video option (`MediaPlayer`/`MediaElement` off-screen render-to-bitmap) if a
  moving source is required. Document the choice in `SIMULATOR.md`; do **not** add ffmpeg/OpenCvSharp
  unless a moving-video acceptance need is proven. Since all simulator code is stripped from Release,
  any dev-only media dep never ships — but keep it light to avoid dev-build bloat.
- Scaling/letterbox is a **pure** helper (`SimMediaScaler`) decoupled from the decoder so it is unit
  testable without any media library.

### Single-source reality — content drives the effect only on the source
[Source: src/Engine/Services/EngineCoordinator.cs:320-321 (`ResolveSource` = the one monitor matching
`SourceMonitorId`), :238 (`_capture.Start(source)` — one capture at a time)]
- The engine starts capture on exactly one source monitor; `EdgeZoneExtractor` extracts edges from that
  source only; all targets project from it (Story 7.5). The simulated capture service therefore only
  ever produces frames for the **source** virtual monitor — that is the content that drives the effect.
- Content assigned to non-source virtual monitors is **visual context**: 10.2 draws it as each
  viewport's background; it does NOT enter the effect pipeline. Document this in `SIMULATOR.md` and the
  selector UI ("source content drives the effect; other monitors show assigned content as context") so
  it reads as faithful product behavior, not a bug. No `EngineCoordinator` / `EdgeZoneExtractor` /
  bridge change.

### Live switch without engine restart
[Source: src/Engine/Capture/IScreenCaptureService.cs:14-15; src/Engine/Services/EngineCoordinator.cs:238]
- `Start` is documented to switch monitors/sources cleanly when already capturing; the simulated source
  mirrors that. On a content-mode/file/mirror change, swap the active `ISimContentSource` then
  `Stop()`/`Start()` the simulated capture source. `DataProcessingService` keeps its latest-frame-wins
  state; the effect runtime keeps running. No `EngineCoordinator` teardown, no window recreation.

### Gating (inherited from 10.1)
[Source: src/Engine/App.xaml.cs:67 (`--minimized` arg precedent), :174 (capture DI seam)]
- All content-source code sits behind `#if SIMULATOR_ENABLED` (Debug-config define added in 10.1) and
  the runtime `--simulator` / `AMBIENTFX_SIMULATOR` gate (same `e.Args.Any(...)` pattern as `--minimized`
  at `App.xaml.cs:67`). The `AmbientFx.csproj` currently defines no `SIMULATOR_ENABLED` constant — 10.1
  introduces it; this story only consumes it. Release publish must contain no simulator IL.

### Testing
- xUnit is the workhorse — no real media library or hardware in CI:
  - `SimMediaScaler` is pure math → table-driven tests (exact-fit / letterbox / crop / tiny).
  - Media source decode → BGRA: use a tiny committed fixture image (e.g. a 2×2 PNG under
    `tests/Engine.Tests/.../fixtures/`); assert dims, tight stride, top-down order, and BGRA channel
    order on a known pixel. Missing-file path: assert one `Error` (Source `"capture"`) raised and a safe
    frame still emitted, no exception escapes.
  - Mirror passthrough: feed a **fake `IScreenCaptureService`** into the mirror adapter (do NOT load
    real WGC in CI); assert re-emitted BGRA equals the fed BGRA at equal resolution (and is rescaled
    correctly at differing resolution), and that the adapter copies before the fed buffer is reused.
    Unavailable/duplicate-of-source monitor → `Error` + safe frame, no throw; switch-away disposes the
    inner service.
  - Live switch: assert content kind changes on a running simulated source without a throw and without
    a coordinator rebuild.
- The real-WGC mirror path itself (actual screen capture of a physical display) is owner/manual
  verification — it cannot run headless in CI. Note it for the owner pass (mirror a real monitor into a
  virtual source slot, confirm the effect reacts to live screen content).

### Out of scope
- **Per-monitor effect/source editing UI beyond the minimal selector** — the full interactive topology
  editor and scenario library are Story 10.5.
- **Feeding non-source content into the effect** — explicitly excluded; the engine is single-source by
  design (AC4). Non-source content is composite background only.
- **Any `ScreenFrameEventArgs` / bridge / `EngineCoordinator` / `EdgeZoneExtractor` change** — the
  contract is fixed; if a payload must change, it is mirrored in `src/Engine/Bridge/` per the standing
  Epic 7/8 guardrail and re-scoped.
- **Heavy video decoding stacks (ffmpeg/OpenCvSharp) by default** — only adopted if a moving-video
  acceptance need is proven; image / image-sequence / in-box video preferred.
- **RGB peripheral and audio content** — RGB readback and the synthetic audio path are Story 10.4.
- **Headless render/automation capture of the composite** — Story 10.5's automation hook.
- **Touching `web/src/shared/simulator.ts`** — that browser fake-bridge is left alone; reuse its
  synthetic-pattern *ideas* in C# only.
