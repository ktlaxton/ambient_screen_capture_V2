# Story 7.5: Position-Aware Edge Glow (True Monitor-Layout Mapping)

## Status
Ready for Review

## Story
**As a** user with monitors of different sizes and placements,
**I want** the edge glow to map to my actual Windows display arrangement — offsets, size
differences, diagonal corners and gaps included —
**so that** the light on each target monitor looks like a physically correct continuation of the
source screen, no matter how my desk is set up.

## Context
Today the glow is only *direction*-aware: `MonitorLayout.ComputeRelation` reduces the layout to
`left | right | above | below | none` from center points, and the effect stretches the **entire**
source edge across the target window. A 24" monitor raised and offset beside a 34" ultrawide shows
colors from parts of the source edge it doesn't physically touch, and the glow lands on the wrong
span of the target. The full geometry needed to fix this is **already delivered** to every effect
window — `WindowConfigPayload.monitor` and `.source` carry virtual-desktop rects — it is simply
unused.

## Acceptance Criteria
1. **True positional mapping.** Each point along the target window's light-entry edge maps to the
   point of the source edge it aligns with in virtual-desktop coordinates (offset- and scale-
   correct). A smaller monitor offset toward the top of the source's right side glows only with
   the colors of the upper, overlapping span of the source's right edge — and that glow occupies
   the matching span of the target edge, not the whole edge.
2. **Nearest-edge projection everywhere.** Layouts with no clean adjacency still glow
   directionally — never falling back to the ambient halo just because the layout is awkward:
   - Target spans that extend past the source edge's ends clamp to the nearest end color.
   - Diagonal (corner-to-corner) targets blend the two nearest source edges (e.g. right + top).
   - A gap between monitors does not change the mapping or attenuate intensity; the projection is
     by alignment, not distance.
   The ambient halo (`relation: 'none'`) remains only for previews/browser (no `windowConfig`)
   and the degenerate same-monitor / zero-area cases.
3. **Live re-layout, no restart.** Rearranging monitors in Windows display settings (drag in
   Settings, resolution change, plug/unplug) re-orients the glow within a couple of seconds while
   the effect keeps running — including when only the **source** monitor's geometry changes
   (today `EffectWindowHost.handleWindowConfig` compares only `source.id`, so source moves/resizes
   are missed; fix this).
4. **Fully automatic.** The Windows display arrangement is the single source of truth. No new
   effect params, no new UI; existing params (`reach`, `spread`, etc.) keep working unchanged.
5. **Reusable layout math.** The projection lives as a pure, unit-tested helper (e.g.
   `web/src/effects/shared/monitorProjection.ts`) usable by other layout-aware effects (aurora and
   audio-bars also read `relation` today and may adopt it later — out of scope to retrofit them
   here, but the helper must not be edge-glow-specific).
6. **No contract break.** `WindowConfigPayload` keeps its current shape (rects already suffice);
   if any bridge type does change, it is mirrored in `src/Engine/Bridge/` per the epic guardrail.
   The simulator (`web/src/shared/simulator.ts`) emits geometry consistent with the new mapping so
   browser dev mode exercises it.
7. **Tests green & extended.** Existing xUnit + Vitest suites stay green. New Vitest coverage for
   the projection helper (offset, partial overlap, contained, diagonal, gap, clamping) and for the
   host's source-geometry re-layout fix. `MonitorLayoutTests` updated/extended if `ComputeRelation`
   semantics change.

## Dev Notes

### The data is already there — this is (almost) all web-side work
[Source: `src/Engine/Bridge/EngineMessages.cs:89-98`, `web/src/shared/bridge.ts:100-106`]
- `WindowConfigPayload = { monitorId, effectId, monitor: MonitorInfo|null, source: MonitorInfo|null, relation }`
  and `MonitorInfo = { id, name, x, y, width, height, isPrimary }` in virtual-desktop pixels.
  The effect window receives both rects today; only `relation` is consumed.
- Expected C# diff: **zero** (or near-zero). `MonitorLayout.ComputeRelation` can stay as-is — it
  still feeds the halo fallback and other effects; do not silently change its semantics.

### Where the current direction logic lives
[Source: `web/src/effects/edge-glow/index.ts:96-122`]
- Constructor switches on `ctx.windowConfig?.relation` to pick `uEntry` (window side light enters)
  and `uRow` (which source-edge row of the 4-row DataTexture feeds it). `uMode=1` is the ambient
  halo. The DataTexture rows are top/bottom/left/right strips resampled to `zones` texels
  (`resampleRow`), so a span remap is a 1D affine transform on the row's U coordinate.

### Geometry model (suggested)
- Work in virtual-desktop coordinates (Y grows downward — see the `above`/`below` comment in
  `MonitorLayout.cs:66`). For a target right of the source: entry edge = target's left edge;
  for each target-edge point `y`, source sample = `(y - source.y) / source.height` clamped 0..1;
  the glowing span of the target edge = the projection of `[source.y, source.y+height]` onto
  `[target.y, target.y+height]`. Symmetric for the other three sides. "Diagonal" = the target's
  projected span on the shared axis has zero length for the primary edge; blend the two edges
  whose corner is nearest.
- Mixed DPI: Windows virtual-desktop coordinates already encode arrangement as the user sees it
  in display settings; no extra DPI math needed (the rects come from `MonitorDetectionService`).

### The one engine-adjacent bug to fix
[Source: `web/src/effect-host/host.ts:59-71`]
- `layoutChanged` compares `prev.source?.id !== cfg.source?.id` but **not** source geometry, and
  effects only read `windowConfig` at `create()`. Moving or resizing the source monitor therefore
  leaves a running glow stale until something else recreates it. Add the source rect fields to the
  comparison (mirror of the existing monitor-rect checks).
- Recreate-on-change is the established pattern (the comment at `host.ts:59` documents it); do not
  add a live `setWindowConfig` path to `EffectInstance` unless it falls out for free.

### Out of scope
- Retrofitting aurora (`web/src/effects/aurora/index.ts:124`) and audio-bars
  (`web/src/effects/audio-bars/index.ts:133`) to positional mapping — they keep `relation`.
- Any capture-side change: `FramePayload.edges` stays the full-edge zone strips; sub-span
  selection happens entirely in the effect.
- New user controls (AC4: fully automatic by decision — see Change Log).

### Testing
- Vitest is the workhorse: the projection helper is pure math — table-driven tests. Host test
  extends the existing `windowConfig adoption` describe block (`web/src/effect-host/host.test.ts`).
- Manual verification (owner hardware): offset dual-monitor setup; drag-rearrange in Windows
  Settings with the effect running; unplug/replug; a diagonal corner arrangement.

### Completion Notes List
- **Geometry model:** for each entry edge, `s` (0..1 along the target edge, desktop direction)
  maps onto the source edge via `e = s * scale + offset` in virtual-desktop coordinates. The
  helper returns up to two `EdgeProjection`s (`entry`, `sourceRow`, `scale`, `offset`, `weight`).
- **Dispatch:** overlap on exactly one axis → single edge (gap size irrelevant — AC2); separated
  on both axes (exact corner included) → two edges weighted `gapX̂/(gapX̂+gapŶ)` with
  resolution-normalized gaps, weights sum to 1; overlapping rects → dominant-center fallback;
  co-located/mirrored (same dead-zone rule as `MonitorLayout.ComputeRelation`) → `[]` → halo.
- **Shader:** chose uniform-array remap over CPU resampling — `uEntry/uRow/uScale/uOffset/uWeight[2]`
  + `uEdgeCount`; `sampleEdge` taps clamp in source coords (nearest-end color beyond the span);
  brightness eases to `SPAN_FLOOR` (0.3) over `SPAN_FADE` (0.3 of the target edge) past the span,
  so partial overlaps read as light wrapping a corner and fully-out-of-span diagonal blends still
  glow (AC2: clamp, don't extinguish). Blur radius is scaled into source units (`* scl`).
- **Fallback chain:** rects → projection; missing/degenerate rects → `projectionFromRelation`
  (identity span, preserves old behavior for older payloads); nothing usable → ambient halo.
  Gallery previews (`windowConfig: null`) keep the halo unchanged.
- **Host fix (AC3):** `layoutChanged` now compares source x/y/width/height (previously only
  `source?.id`), so moving/resizing the source monitor recreates running effects. C# side already
  re-pushes on `SystemEvents.DisplaySettingsChanged` — verified, untouched.
- **Simulator (AC6):** relation was hardcoded `'right'` for every window (wrong for the sim's
  top monitor); now computed from rects with the same dead-zone rule, the source follows
  `settings.sourceMonitorId`, and `setSourceMonitor` re-pushes `windowConfig` like the engine.
- **Not retrofitted (per story scope):** aurora/audio-bars still read `relation` only.
- **Runtime smoke (headless Chrome + SwiftShader, simulator bridge):** shader compiles and links
  (one benign D3D X3595 warning — gradient in a varying loop; the DataTexture has no mips, so
  derivatives are irrelevant); DISPLAY2 (right of source) renders left-entry spill, DISPLAY3
  (above, offset) renders bottom-entry spill — both directional paths verified on-GPU.
- **Manual verification remaining (owner hardware):** real offset dual-monitor look, live
  drag-rearrange in Windows Settings, unplug/replug, diagonal corner arrangement.
