# Story 10.1: Simulated Topology & Capture (Headless Engine Harness)

## Status
Ready for Review

## Story
**As a** developer,
**I want** the real engine to run end-to-end against a fabricated monitor topology fed by synthetic
frames, gated to dev builds only,
**so that** the projection / relation / window-config pipeline can be exercised on any layout —
three-wide, L-shape, vertical stack, mixed-DPI, portrait, a six-panel wall — without real monitors
and without shipping a single byte of it in the signed product.

## Context
The pipeline is built to handle *any* Windows display arrangement (the whole point of Story 7.5's
positional projection), but on a 2-monitor dev machine the layouts the product must support cannot
be exercised at all. Epic 10 fixes that with an in-app Layout Simulator that swaps four DI seams for
simulated implementations and composites every virtual monitor into one window.

This first story is the **foundation the other four build on**: it replaces the two seams that
*originate* topology and pixels — `IMonitorDetectionService` (`App.xaml.cs:179`) and
`IScreenCaptureService` (`App.xaml.cs:174`) — with simulated implementations driven by JSON
scenario fixtures, and gates all of it behind a compile-time `SIMULATOR_ENABLED` constant (Debug
config only) plus a runtime `--simulator` / `AMBIENTFX_SIMULATOR` switch. The real
`EngineCoordinator`, `DataProcessingService`, `EdgeZoneExtractor`, `MonitorLayout`, and the bridge
all run **unmodified** — the simulated services satisfy the existing interfaces exactly, so the
coordinator's topology-change re-sync path (`EngineCoordinator.cs:1108-1141`) and capture-start path
(`EngineCoordinator.cs:238`) execute against fabricated input with zero forking.

Effect *windows* are **not rendered here** — that is Story 10.2. In this story the engine runs
**headless**: there is no composite window yet, and validation is by asserting the
`WindowConfigPayload`s / relations the coordinator produces (the same data 10.2 will draw) plus unit
tests on the two simulated services. The deliverable is correct, test-covered engine behavior on
any fabricated layout, behind dev-only gating, with the existing `SIM_MONITORS` arrangement
reproduced as the first JSON fixture.

## Acceptance Criteria
1. **`SimulatedMonitorDetectionService : IMonitorDetectionService`.** A drop-in implementation of
   every interface member (`GetMonitors()`, `StartMonitoring()`, `StopMonitoring()`,
   `event EventHandler? MonitorsChanged`, `Dispose()`) that serves a topology loaded from a JSON
   scenario instead of enumerating real displays. Monitors carry synthetic but **stable** `Id`s
   (e.g. `\\.\SIM-DISPLAY1`), real virtual-desktop `X/Y/Width/Height` (negative coordinates valid for
   left/above primary), an `IsPrimary` flag, and a **sentinel `HMonitor`** (e.g. `IntPtr.Zero` or a
   distinctive non-handle value) that never reaches WGC because capture is also simulated. Exactly one
   monitor is primary per the loaded scenario. `GetMonitors()` returns a fresh snapshot each call,
   mirroring the real impl's contract (`MonitorDetectionService.cs:44-45`).
2. **On-demand topology mutation + `MonitorsChanged`.** The simulated service exposes dev-facing
   methods to mutate the live topology — add a monitor, remove a monitor, change a monitor's
   resolution, and change orientation (portrait via `Width`/`Height` swap; see Dev Notes on the
   no-rotation-field decision) — and a `FireMonitorsChanged()` that raises `MonitorsChanged` on a
   background (non-UI) thread, exactly as the real service does from its debounce timer
   (`MonitorDetectionService.cs:171`). Firing it drives the **real** coordinator re-sync path
   (`EngineCoordinator.cs:1108-1141`) unchanged: re-enumerate, re-post `Monitors`, re-validate the
   source, re-sync effect windows, re-push window configs.
3. **`SimulatedScreenCaptureService : IScreenCaptureService`.** A drop-in implementation of every
   interface member (`bool IsCapturing`, `Start(MonitorInfo)`, `Stop()`,
   `event EventHandler<ScreenFrameEventArgs> FrameCaptured`, `event EventHandler<PipelineErrorEventArgs> Error`,
   `Dispose()`) that emits synthetic test-pattern BGRA frames for the started monitor at that
   monitor's source resolution. It honors the established frame contract: tightly-packed 32-bit BGRA
   (B@0/G@1/R@2/A@3), top-down rows, **no stride padding** (`stride = width*4`), and a buffer that is
   **reused per frame** so the subscriber copies synchronously (`IScreenCaptureService.cs:26-35`,
   `ScreenCaptureService.cs:28-35`). Frame emission is rate-limited to a configurable `maxFps`.
4. **At least three synthetic patterns.** `SimulatedScreenCaptureService` ships at minimum an
   **animated gradient** (deterministic function of frame index — moving so the pipeline sees change
   frame-to-frame), **color bars**, and a **test card**. Patterns are chosen per scenario / per
   monitor (the assignment plumbing it down to 10.2/10.3 may be minimal here, but the pattern set
   exists and is selectable). The buffer is generated/filled in-place into the reused buffer (no
   per-frame allocation once warm, matching `ScreenCaptureService` design).
5. **Correct on source switch; never throws (NFR5).** Calling `Start(MonitorInfo)` while already
   capturing switches to the new monitor and re-sizes the synthetic buffer to the new monitor's
   resolution (mirrors the real "switches monitors internally if already capturing" contract,
   `IScreenCaptureService.cs:14`, `EngineCoordinator.cs:238`). `IsCapturing` reflects state.
   `Start`/`Stop`/`Dispose` are idempotent and **never throw back into the pipeline** — any internal
   fault is caught and surfaced via the `Error` event, never as an exception (NFR5, matching the real
   service's defensive posture).
6. **Dev-only gating — compile-time.** A `SIMULATOR_ENABLED` `DefineConstant` is added in
   `AmbientFx.csproj` for the **Debug configuration only**. All simulator code (the two new services,
   their DI registration override, the launch branch) is wrapped in `#if SIMULATOR_ENABLED`. A
   **Release** build defines no such constant, so the simulator IL is compiled out entirely.
7. **Dev-only gating — runtime.** Even in a Debug build, the simulator is **off** unless explicitly
   selected by a `--simulator` command-line arg (precedent: `--minimized`, `App.xaml.cs:67`) or an
   `AMBIENTFX_SIMULATOR` environment variable. When neither is present the app composes the real
   `ScreenCaptureService` / `MonitorDetectionService` exactly as today. The selection logic itself
   lives inside `#if SIMULATOR_ENABLED`.
8. **Zero shipped-build impact.** The Release/Velopack publish (`build.ps1`, `-c Release` →
   `vpk pack`, lines 76-114) contains **no simulator IL** and is byte-for-byte unaffected. There is
   **zero** change to Free/Premium licensing, entitlements, or packaging. The bridge contract
   (`src/Engine/Bridge/`) is **unchanged** — the simulated services satisfy existing interfaces only.
9. **JSON scenario fixture format defined.** A documented, versioned JSON schema describes a topology:
   per-monitor `id`, `name`, `x`, `y`, `width`, `height`, `isPrimary`, plus capture-side fields the
   later stories extend (at minimum a `pattern` selector and `maxFps`). The existing web simulator's
   `SIM_MONITORS` arrangement (`web/src/shared/simulator.ts:33-36`) is reproduced verbatim as the
   first checked-in fixture (DISPLAY1 primary 2560×1440 @ (0,0); a 1920×1080 right monitor @
   (2560,180); a 1920×1080 top monitor @ (320,−1080)). Loading is defensive: malformed/missing files
   degrade to a clear log + a sane default topology, never a crash.
10. **Tests green & extended.** New xUnit coverage: (a) `SimulatedScreenCaptureService` BGRA
    correctness (packing, top-down, stride, buffer reuse, resolution-follows-source, source switch,
    `maxFps`, never-throws); (b) `SimulatedMonitorDetectionService` fixture load, all interface
    members, mutation methods, and `MonitorsChanged` firing; (c) a **coordinator integration test**
    that wires the simulated detection service into the real `EngineCoordinator` and asserts the
    correct `WindowConfigPayload` / `Relation` set across **several** fabricated topologies (3-wide,
    L-shape, vertical stack, mixed-resolution), including a `FireMonitorsChanged()` re-sync.
    The existing xUnit + Vitest suites stay **green**.

## Dev Notes

### The two seams that originate topology and pixels — both already abstracted
[Source: `src/Engine/Services/IMonitorDetectionService.cs:9-19`, `src/Engine/Capture/IScreenCaptureService.cs:10-24`, `src/Engine/App.xaml.cs:174,179`]
- `IMonitorDetectionService` is the smaller interface: `GetMonitors()` (line 12),
  `StartMonitoring()`/`StopMonitoring()` (14-15), `event EventHandler? MonitorsChanged` (line 18 —
  note it is the **plain** `EventHandler`, *not* a custom args type; pass `EventArgs.Empty`), and
  `Dispose()` via `IDisposable` (line 9). The real impl (`MonitorDetectionService.cs`) hooks
  `SystemEvents.DisplaySettingsChanged` (`:111`), debounces 500 ms (`:25`, `:149`), and raises
  `MonitorsChanged` on a **ThreadPool timer thread** (`:171`). The simulator skips all OS interop —
  `StartMonitoring`/`StopMonitoring` just flip an armed flag, and `FireMonitorsChanged()` raises the
  event off the UI thread to match the real timing contract.
- `IScreenCaptureService`: `IsCapturing` (`:12`), `Start(MonitorInfo)` (`:15`, "switches monitors
  internally if already capturing" `:14`), `Stop()` (`:17`),
  `event EventHandler<ScreenFrameEventArgs> FrameCaptured` (`:20`), `event EventHandler<PipelineErrorEventArgs> Error`
  (`:23`), `IDisposable` (`:10`). DI singletons at `App.xaml.cs:174` (capture) and `:179`
  (detection) — the simulator overrides exactly these two registrations under `#if SIMULATOR_ENABLED`.

### The frame contract the simulated capture MUST honor
[Source: `src/Engine/Capture/IScreenCaptureService.cs:26-35`, `src/Engine/Capture/ScreenCaptureService.cs:28-35,46`, `src/Engine/Processing/DataProcessingService.cs:247-276`]
- `ScreenFrameEventArgs` = `{ byte[] PixelsBgra, int Width, int Height, double TimestampMs }`
  (`IScreenCaptureService.cs:27-35`, all `required`/`init`). The buffer is **tightly packed 32-bit
  BGRA, top-down rows, no padding** (`stride = Width*4`), B@0/G@1/R@2/A@3.
- The buffer is **reused per frame** — the documented rule (`ScreenCaptureService.cs:28-35`) is that
  subscribers consume/copy **synchronously**. The downstream consumer
  `DataProcessingService.OnFrameCaptured` does exactly that: validates
  `pixels.Length >= Width*Height*4` (`:251-259`) then `Buffer.BlockCopy` into its own store
  (`:266`). So the simulator may safely reuse one buffer and the existing pipeline is correct as-is.
- `FrameCaptured` fires on threadpool/worker threads in the real impl
  (`ScreenCaptureService.cs:31`). A timer-driven simulated raise (also off the UI thread) matches.
- The real capture **downscales to a ~64 px-wide mip before readback** (`ScreenCaptureService.cs:46`
  `TargetMipWidth = 64`). The engine downsamples internally (`EdgeZoneExtractor`), so emitting the
  synthetic pattern at **full source resolution** is fine — the pipeline shrinks it. Don't
  pre-shrink; emit at `monitor.Width × monitor.Height` to keep fidelity with what the real seam sees.
- Reuse the BGRA packing convention from `SyntheticFrames`
  (`tests/Engine.Tests/Processing/EdgeZoneExtractorTests.cs:12-29`): `b@p, g@p+1, r@p+2, 255@p+3`,
  `p = (y*width + x)*4`. That helper is test-only; the production pattern generators live in
  `src/Engine/Simulator/` but should match its byte order exactly.

### `MonitorInfo` — no rotation field; portrait is just `width < height`
[Source: `src/Engine/Models/MonitorInfo.cs:8-25`]
- Fields: `Id` (stable string device path), `Name`, `X`, `Y`, `Width`, `Height` (device px,
  virtual-desktop coords — **negative is valid** for monitors left of / above primary), `IsPrimary`,
  and `HMonitor` (`nint`, `[JsonIgnore]` at `:23-24`, ephemeral). There is **no rotation/orientation
  field**. Model portrait by swapping `Width`/`Height` in the fixture / `SetOrientation`. Do **not**
  add an orientation flag to `MonitorInfo` for this story — it would ripple into the bridge and break
  the "no contract change" invariant. Only introduce an explicit orientation marker if a later test
  demands distinguishing "rotated 1080×1920" from "native portrait", and even then prefer a
  simulator-local concept over a `MonitorInfo` field.
- `HMonitor` must be a **sentinel** in the simulator (e.g. `IntPtr.Zero`). It never reaches WGC
  because `SimulatedScreenCaptureService` never calls `CaptureInterop.CreateItemForMonitor` (the real
  path that consumes it, `ScreenCaptureService.cs:205`). Capture being simulated is what makes the
  sentinel safe.

### The real coordinator re-sync path that mutation drives — unmodified
[Source: `src/Engine/Services/EngineCoordinator.cs:133,238,320-321,1108-1145`]
- Subscription: `_monitorDetection.MonitorsChanged += OnMonitorsChanged` (`:133`); start at `:147`
  via `StartMonitoring()`.
- `OnMonitorsChanged` (`:1108`) bails on shutdown then marshals to the dispatcher
  (`BeginInvoke(HandleMonitorsChangedOnUi)`, `:1114-1115`). `HandleMonitorsChangedOnUi` (`:1119`):
  re-`GetMonitors()` (`:1126`) → `PostToControl(Monitors, BuildMonitorsPayload())` (`:1128`) →
  `ResolveSource()` existence check (`:1130-1136`) → if still enabled,
  `SyncEffectWindowsSafeAsync(BuildSpecs())` (`:1140`) + `PushWindowConfigs()` (`:1141`) →
  `PushConfig()` (`:1144`). The simulator changes **none** of this; `FireMonitorsChanged()` simply
  feeds it fabricated topology.
- `ResolveSource()` (`:320-321`) matches `_settings.SourceMonitorId` against the (now simulated)
  monitor list — so the scenario's source id must be one of the fixture ids. Capture is started via
  `_capture.Start(source)` (`:238`); with the simulated capture that just kicks the pattern timer.

### What the headless harness asserts (10.2 draws it; 10.1 proves it's right)
[Source: `src/Engine/Services/EngineCoordinator.cs:324-360,972`, `src/Engine/Bridge/EngineMessages.cs:122-131`, `src/Engine/Services/MonitorLayout.cs:25-68`]
