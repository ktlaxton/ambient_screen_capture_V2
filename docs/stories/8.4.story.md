## Story
**As the** owner shipping this app to other people's machines,
**I want** the RGB peripheral feature to install, license, and degrade correctly on machines that
may not have iCUE (or any RGB vendor software),
**so that** the distributable is legally clean and behaves gracefully for every user — RGB hardware
or not.

## Context
Stories 8.1–8.3 add RGB.NET (LGPL-2.1) and its native vendor SDK bits to the app. Story 7.4 already
ships a self-contained Velopack installer with code signing and auto-update. This story closes the
gap between the two: it makes sure the LGPL obligations are met, the native dependencies are bundled
or located correctly, and a **clean machine with no iCUE and no RGB hardware** installs and runs the
app with the peripheral feature simply dormant — no crashes, no scary errors, no missing-DLL
failures.

## Acceptance Criteria
1. **LGPL-2.1 compliance review (sign-off).** RGB.NET and its components are confirmed dynamically
   linked (NuGet, unmodified), the license + a written notice are included in the distribution, and
   the relink/replace path is documented. This is an explicit go/no-go gate recorded in the story —
   the legal posture for shipping the dependency is settled, not assumed.
2. **Native dependencies bundle correctly.** The native runtime bits RGB.NET pulls in (iCUE SDK
   native library and any per-vendor natives from 8.3) are included in the Velopack publish output
   and resolve at runtime from the installed app — no "DLL not found" on a machine without dev tools.
3. **Clean-machine graceful absence.** On a fresh VM with **no iCUE installed and no RGB hardware**,
   the app installs, launches, and runs fully; the peripheral feature shows its normal "not
   available" state (from 8.1 AC2) and the user is, at most, gently informed iCUE is needed for RGB
   peripherals — never an exception, hang, or startup failure.
4. **Auto-update preserves device config.** A Velopack update from a prior version preserves the
   user's peripheral settings (enable, brightness, per-device placement from 8.2, provider flags from
   8.3) — the back-compat settings rules hold across the update.
5. **Installer size/footprint acknowledged.** Any meaningful installer-size or startup-time impact
   from the RGB.NET + native bits is measured and noted; if a provider is heavy, document the
   trade-off (and that non-Corsair providers default off — Story 8.3 AC3).
6. **Docs updated.** `docs/RELEASING.md` (and any build script touched by 7.4) reflect the added
   native dependencies and the LGPL notice step, so a release is reproducible.
7. **Verification on a clean VM.** The above is verified by installing the signed build on a clean
   Windows VM (no iCUE, no RGB software) and on the owner's real-hardware machine, confirming both
   the dormant path and the working path. (Recorded in QA Results.)

## Dev Notes

### LGPL-2.1 compliance review (AC1, performed 2026-06-12)
Facts established against the actual Release publish output:
1. **Unmodified + dynamically linked.** All RGB.NET components arrive as stock NuGet
   assemblies (`RGB.NET.Core` + 7 device providers, v3.2.0) and remain separate DLLs in the
   publish output — the project sets no `PublishSingleFile`, `PublishTrimmed`, or merging,
   and `build.ps1` now fails the build if the assemblies stop being separate files.
2. **License + notice ship.** `licenses/LGPL-2.1.txt` (full text from gnu.org) and
   `THIRD-PARTY-NOTICES.md` are copied into every build and land in the installed app
   directory.
3. **Relink/replace path documented** in `THIRD-PARTY-NOTICES.md`: users can rebuild
   RGB.NET from source and drop in replacement DLLs at
   `%LocalAppData%\AmbientFx\current\`; the caveat that auto-updates reinstall shipped
   assemblies is stated.
4. **Adjacent licenses:** the Corsair iCUE SDK native DLL is redistributed under Corsair's
   SDK terms (permits redistribution with applications); it is not LGPL and not linked into
   our code — RGB.NET loads it at runtime.

**Assessment:** the standard obligations of LGPL-2.1 §6 for a proprietary work using the
library via a shared-library mechanism are met. **Recommendation: GO.**
**Owner sign-off:** ☐ pending — Kirk to check this box (or note objections) before the
first public release that includes RGB.NET.

### Build on Story 7.4's pipeline
[Source: Story 7.4 (Velopack installer, signing, auto-update), `docs/RELEASING.md`]
- 7.4 established the one-command build (web → wwwroot → publish → Velopack) and the auto-update feed.
  This story extends that output to carry the RGB.NET native dependencies and the LGPL notice. Don't
  re-architect the installer — augment it.

### The clean-machine path is the real risk
- Dev machines have iCUE and hardware; the failure mode hides until a clean install. The 8.1 absence
  handling (AC2) must be exercised against an actual packaged, signed build on a VM with nothing RGB
  installed — that's where missing-native-DLL and first-launch crashes surface. Treat AC3 as the
  headline acceptance test.

### Licensing is a gate, not a checkbox
- LGPL-2.1 dynamic linking in a closed-source app is generally fine, but it carries real obligations
  (provide the library's license, allow the user to relink a modified RGB.NET). This story is where
  that's actually confirmed and documented before the dependency reaches users — flagged since Epic 8
  was created and as a guardrail on 8.1.

### Scope
- This is **packaging/licensing/clean-machine** hardening only — no new device features (those are
  8.1–8.3). It is the "ship it safely" story for the epic.

### Testing
- A settings back-compat/migration test for AC4. Everything else is integration verification on a
  clean VM and on owner hardware (AC7) — the parts that a unit test can't reach.
