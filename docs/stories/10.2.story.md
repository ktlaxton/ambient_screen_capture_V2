# Story 10.2: Composite Simulator Window (See the Effects)

## Status
Ready for Review

## Story
**As a** developer/QA,
**I want** every virtual monitor and its real effect composited into one window laid out as the
virtual desktop — source content behind each viewport, the live effect on top —
**so that** I can visually verify projection correctness and effect look across any monitor layout
on a 2-monitor machine, without forking a single line of the projection, effect, or bridge code.

## Context
Story 10.1 gives the engine a fabricated topology (`SimulatedMonitorDetectionService`) fed by
synthetic frames (`SimulatedScreenCaptureService`), gated behind `SIMULATOR_ENABLED` + `--simulator`.
But 10.1 runs **headless**: it suppresses effect-window creation in sim mode and validates only the
`WindowConfigPayload`/relation math via assertions. You cannot *see* anything.

Today each target monitor gets its own real OS window: `EffectWindow : Window`, one per monitor,
created and owned by `WebViewWindowManager` and placed in **device pixels** via `SetWindowPos` at the
monitor's real desktop rect [Source: `src/Engine/Hosting/EffectWindow.cs:181-183`]. On a 2-monitor
machine that mechanism can only ever paint 2 physical screens — a fabricated six-panel wall has
nowhere to land.

This story introduces the one seam the epic's Architecture diagram calls for: an
`IEffectSurfaceHost` abstraction that `WebViewWindowManager` builds through an **injected factory**
instead of `new EffectWindow(...)`. The production path keeps using `EffectWindow` (the real
`SetWindowPos` placement, byte-for-byte unchanged). The simulator path swaps in
`SimulatorEffectSurface` — a child WebView2 hosted inside one `SimulatorWindow` whose `Canvas` lays
out N viewports as a **scaled** copy of the virtual desktop (negative coords, gaps, mixed sizes
preserved). Each viewport draws its source monitor's content as a background and composites the
**real** effect runtime on top. Because the surfaces receive the genuine `WindowConfigPayload` from
the real `EngineCoordinator` and run the unmodified `monitorProjection.ts`, what you see is the real
projection on the real layout — only scaled to fit a window.

This is the hardest story in the epic: it is the one that produces the visual tool, and the one most
at risk of accidentally forking the pipeline. The fidelity invariant below is non-negotiable.

## Acceptance Criteria
1. **`IEffectSurfaceHost` abstraction, production path proven unchanged.** A new
   `IEffectSurfaceHost` interface mirrors exactly the surface API `EffectWindow` already exposes
   (`MonitorId`; `Task InitializeWebViewAsync(CoreWebView2Environment)`; `void RepositionTo(MonitorInfo)`;
   `bool TryPostWebMessage(string)`; `event EventHandler<string>? BridgeMessageReceived`;
   `event EventHandler? PageReady`; `void Dispose()` / closeable). `EffectWindow` implements it with
   **zero behavior change** — its production code path is still `SetWindowPos` at the device-pixel
   monitor rect, still kiosk/no-activate/topmost, still disposes its WebView2 on close. The unit
   suite asserts the production path is unaltered (see AC 8).
2. **Injected surface factory in `WebViewWindowManager`.** The manager builds surfaces via an
   injected `Func<MonitorInfo, IEffectSurfaceHost> surfaceFactory` instead of constructing
   `EffectWindow` directly. The default (production) factory returns `new EffectWindow(monitor, logger)`,
   wired in DI so production behavior is identical. `EffectEntry.Window` becomes `EffectEntry.Surface`
   (typed `IEffectSurfaceHost`); every `.Window` call site is migrated. The bridge, `EngineCoordinator`,
   `WindowConfigPayload`, and `EffectWindowSpec` are **untouched**.
3. **`SimulatorEffectSurface` hosts the real runtime in a viewport.** `SimulatorEffectSurface : Control,
   IEffectSurfaceHost` hosts a child `WebView2` that navigates to the **same** effect runtime URL as
   `EffectWindow` (`WebViewHelpers.EffectUrl(monitorId)`), with the same kiosk lockdown and the same
   render-process-crash reload behavior. `RepositionTo(monitor)` updates the control's
   `Canvas.Left/Top/Width/Height` (in scaled coordinates) instead of calling `SetWindowPos`. It
   forwards `BridgeMessageReceived` and `PageReady` from its WebView2 identically to `EffectWindow`.
4. **`SimulatorWindow` renders the virtual desktop to scale.** A `SimulatorWindow : Window` hosts a
   `Canvas` containing N `SimulatorEffectSurface` viewports laid out as a scaled mapping of the
   monitor rects: a single bounding box is computed over all virtual-desktop rects and one uniform
   scale factor maps it into the window's client area. Negative coordinates, inter-monitor gaps, and
   mixed monitor sizes are all preserved (the layout looks like the Windows "Display" arrangement
   diagram). Each viewport shows its source monitor's content (the synthetic/media/mirror frame from
   10.1) as its background, with the live effect surface composited on top.
5. **Live re-layout on scenario or topology change, no restart.** When 10.1 fires `MonitorsChanged`
   (scenario swap, add/remove monitor, resize/reorient), the composite recomputes the bounding box +
   scale, repositions every existing viewport, creates/removes viewports for added/removed monitors,
   and re-pushes the fresh `WindowConfigPayload` to each — the effect re-orients within a second or
   two while running, with no app restart. This rides the existing
   `EngineCoordinator.HandleMonitorsChangedOnUi → SyncEffectWindowsAsync + PushWindowConfigs` path
   unchanged.
6. **Per-monitor effect assignment works in the composite.** Assigning a different effect to a virtual
   monitor (global or per-monitor override) swaps that viewport's effect live, exactly as it does for
   real `EffectWindow`s — driven by the same `windowConfig` re-push, with no simulator-specific
   command handling.
7. **Fidelity guardrail — real config, unmodified projection, scaling only.** Each
   `SimulatorEffectSurface` receives the **real** `WindowConfigPayload` produced by the real
   `EngineCoordinator.BuildWindowConfigFor` (carrying the true virtual-desktop `monitor`/`source`
   rects and `MonitorLayout.ComputeRelation` relation) — it is **not** rerouted through
   `web/src/shared/simulator.ts`. The effect runs `monitorProjection.ts` and the effect runtime
   **unmodified**. The only adaptation permitted is canvas scaling of the host viewport; the projection
   math operates on the genuine rects, so what renders is the real projection for that layout.
8. **Production-path-unchanged + abstraction tests.** xUnit tests cover: the `IEffectSurfaceHost`
   contract; that `EffectWindow` still implements every member with no behavioral change (a
   construction/placement assertion using the existing native-call seam or a thin spy, no real
   monitors); that `WebViewWindowManager` builds surfaces through the injected factory and migrating
   `EffectEntry` left create/reposition/close/dispose semantics intact; and a smoke test that N fake
   surfaces (1, 3, 6) are instantiated by `SyncEffectWindowsAsync`, each `RepositionTo`'d and handed
   its config envelope. All simulator test code is `SIMULATOR_ENABLED`-gated.
9. **1–6 monitors with a documented, guarded multi-WebView2 ceiling.** The composite supports 1 to 6
   virtual monitors. Because each viewport is a separate WebView2 sharing one
   `CoreWebView2Environment` (one browser process, GPU resources fan out per render process), the
   simulator documents and guards an upper ceiling: layouts beyond the supported count surface a clear
   in-tool warning rather than silently exhausting GPU memory or spawning unbounded render processes.
10. **Suites green; no production drift.** Existing xUnit + Vitest suites stay green. The Release /
    Velopack build contains no simulator IL (`SimulatorWindow`, `SimulatorEffectSurface`, and the
    sim factory are inside `#if SIMULATOR_ENABLED`); the production `EffectWindow`/`WebViewWindowManager`
    diff is the factory seam only, with zero Free/Premium or packaging impact. No bridge-contract change.

## Dev Notes

### Fidelity invariant (the whole point of this story)
The simulator MUST reuse the real pipeline **unmodified**: `EngineCoordinator`,
`MonitorLayout.ComputeRelation`, `monitorProjection.ts`, the effect runtime, `LedProjection`, and
`AudioModulation` are not forked, and there is **no bridge-contract change**. Canvas scaling of the
host viewport is the *only* adaptation permitted. If a simulator surface ever reads a fabricated
`WindowConfigPayload` (e.g. one synthesized by `web/src/shared/simulator.ts`) instead of the real one
from `EngineCoordinator.BuildWindowConfigFor`, the test is no longer valid — the projection must run
on the genuine virtual-desktop rects. [Source: `src/Engine/Services/EngineCoordinator.cs:353-360`,
`web/src/effects/shared/monitorProjection.ts:1-45`]

### Today's per-monitor window mechanism (what we are abstracting)
[Source: `src/Engine/Hosting/EffectWindow.cs:20-67,107-119,123-144,165-187`]
- `EffectWindow : Window` — one borderless, topmost, kiosk window per monitor. Constructed
  `EffectWindow(MonitorInfo monitor, ILogger logger)`; exposes `MonitorId` (`:30`), events
  `BridgeMessageReceived` (`:35`) and `PageReady` (`:39`), and methods
  `InitializeWebViewAsync(CoreWebView2Environment)` (`:74`), `RepositionTo(MonitorInfo)` (`:107`),
  `TryPostWebMessage(string)` (`:123`).
- Kiosk styling: `WindowStyle.None`, `Topmost=true`, `ShowInTaskbar=false`, `ShowActivated=false`,
  `Focusable=false`, `AllowsTransparency=false` (`:48-57`); `WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`
  applied in `OnSourceInitialized` (`:169`). **These styles are window-level and do not carry to a
  child `Control`** — see Risks.
- Placement is **device pixels** via `SetWindowPos(hwnd, HWND_TOPMOST, monitor.X, monitor.Y,
  monitor.Width, monitor.Height, ...)` in `ApplyMonitorBounds` (`:181-183`); `RepositionTo` re-applies
  it on a bounds change (`:107-119`). The whole comment block at `:14-17,:177-180` explains why DIPs /
  `WindowState.Maximized` are forbidden (mixed-DPI trap) — the simulator side-steps all of this by
  composing into one window and scaling, which is exactly why it can only *approximate* per-monitor DPI
  (Out of scope / Risks).
- Crash recovery: `OnProcessFailed` reloads on `RenderProcessExited` off the callback (`:218-240`);
  `OnClosed` disposes the WebView2 (`:146-163`). Mirror both in `SimulatorEffectSurface`.

### The manager seam to introduce
[Source: `src/Engine/Hosting/WebViewWindowManager.cs:29,234-242,283-298,473-533,569-576`]
- `_effectWindows` is a `Dictionary<string, EffectEntry>` keyed by monitor id (`:29`); `EffectEntry`
  holds `Window`, a coalescing `Target` (`PostTarget`, 60fps latest-wins), and `ConfigJson` (`:569-576`).
- Construction site to swap: `var window = new EffectWindow(spec.Monitor, _logger);` (`:234`) →
  `_surfaceFactory(spec.Monitor)`. The factory should return an `IEffectSurfaceHost`; the entry then
  subscribes `BridgeMessageReceived`/`PageReady` (`:241-242`) and stores it as `Surface`.
- `.Window` references to migrate to `.Surface`: reposition + config re-push on an existing entry
  (`:228,:230`), the high-frequency frame fan-out uses `entry.Target` (`:283-286`) so it is unaffected,
  the low-frequency `TryPostWebMessage` fan-out (`:294-296`), `OnEffectPageReady` replay (`:480`),
  `CloseEffectWindow` (`:501`), `CloseAllWindows` (`:519`).
- `Show()`: the manager calls `window.Show()` then `InitializeWebViewAsync` (`:250-251`). A
  `SimulatorEffectSurface` is added to a `Canvas`, not `Show()`n. Cleanest seam: keep `Show()` off the
  interface and have the **production factory** wrap creation so the manager calls a single
  lifecycle method, OR add an `Activate()`/no-op `Show()` to the interface. Pick one and keep the
  production call sequence identical.
- The sync engine itself (`SyncCoreAsync` at `:181`, the supersede/serialize logic, identity-checked
  eviction) is untouched — it operates purely through the entry's surface + target.

### Config + relation come from the real engine, per monitor
[Source: `src/Engine/Services/EngineCoordinator.cs:324-360,1119-1145`,
`src/Engine/Bridge/EngineMessages.cs:122-131`]
- `BuildSpecs` (`:324-351`) emits one `EffectWindowSpec { Monitor, Config }` per target; `Config` is
  `BuildWindowConfigFor(monitor, source)` (`:353-360`) carrying the true `Monitor`/`Source`
  `MonitorInfo` rects and `Relation = MonitorLayout.ComputeRelation(source, monitor)`.
- `WindowConfigPayload` (`EngineMessages.cs:122-131`) is the bridge type the effect reads; **do not
  change its shape** (Story 7.5/Epic guardrail — rects already suffice).
- The re-sync path on topology change: `OnMonitorsChanged → HandleMonitorsChangedOnUi` re-pulls
  monitors, then for an enabled engine calls `SyncEffectWindowsSafeAsync(BuildSpecs())` +
  `PushWindowConfigs()` (`:1140-1141`). The composite gets live re-layout for free by riding this — no
  new coordinator code. The 10.1 `SimulatedMonitorDetectionService.MonitorsChanged` is what fires it.

### Effect runtime is the production runtime
[Source: `web/src/effect-host/host.ts:53-76`, `web/src/effects/shared/monitorProjection.ts:1-45`,
`src/Engine/Hosting/WebViewHelpers.cs:32-33`]
- Both `EffectWindow` and `SimulatorEffectSurface` navigate to `WebViewHelpers.EffectUrl(monitorId)`
  (`effects.html?monitorId=...`), served from the same virtual host (`MapVirtualHost`, `:47-49`).
- `host.ts handleWindowConfig` (`:53-76`) already recreates the effect on a layout/source-geometry
  change (the Story 7.5 fix at `:61-72`), so live re-orient works with no host change — the simulator
  just feeds it the real, changing configs.

### DI / gating wiring
[Source: `src/Engine/App.xaml.cs:170-192,67`]
- The `IWebViewWindowManager` singleton (`:177`) gains the surface-factory dependency. The production
  registration supplies the `EffectWindow` factory. The simulator path (selected by the 10.1
  `--minimized`-style `--simulator` arg / `AMBIENTFX_SIMULATOR` env at `App.OnStartup`, precedent at
  `:67`) supplies the `SimulatorWindow`'s factory instead — all `#if SIMULATOR_ENABLED`. Release publish
  strips it; no Free/Premium/packaging impact.

### Risks (call out and mitigate)
- **DPI/scaling fidelity.** Production places windows in device pixels per monitor; the composite uses
  one window + a uniform scale, so per-monitor PerMonitor-V2 DPI is *approximated*, not reproduced.
  Document this clearly — projection geometry stays correct (it is rect-based), but exact pixel/DPI
  look is not a substitute for owner hardware verification (Out of scope).
- **N concurrent WebView2 GPU memory.** All surfaces share one `CoreWebView2Environment` (one browser,
  fan-out render processes). Six WebGL contexts can pressure GPU memory; hence the 1–6 ceiling + guard
  (AC9). Consider a documented soft cap and a warning rather than unbounded creation.
- **Per-child render-process crash recovery.** Each surface must independently survive a render-process
  exit and reload, mirroring `EffectWindow.OnProcessFailed` — a crashed viewport must not take down the
  composite. [Source: `src/Engine/Hosting/EffectWindow.cs:218-240`]
- **Kiosk/no-activate styles don't propagate to a child `Control`.** `WS_EX_TOOLWINDOW`/`NOACTIVATE`
  and `Focusable=false` are window-level on `EffectWindow`; `SimulatorEffectSurface` is a child control
  in one window, so set `Focusable=false` / `IsHitTestVisible` on the control + its WebView2 and rely on
  `SimulatorWindow` for activation policy. Verify the child WebView2 doesn't steal focus per frame.

### Testing
- xUnit is the workhorse (no real monitors, no GPU in CI). Inject a fake `IEffectSurfaceHost` factory
  into `WebViewWindowManager` that records per-monitor `InitializeWebViewAsync`/`RepositionTo`/
  `TryPostWebMessage`/close calls, and assert: create-on-new, reposition+re-push-on-existing, close-on-
  removed across 1/3/6-monitor spec lists driven through `SyncEffectWindowsAsync`. This reuses the
  `CoordinatorHarness` mock-everything pattern. [Source: `tests/Engine.Tests/Coordinator/CoordinatorHarness.cs:38,54`]
- Assert the production path is unchanged: `EffectWindow` still implements every `IEffectSurfaceHost`
  member, and the default DI factory yields an `EffectWindow`. The actual `SetWindowPos` placement is
  not unit-testable without a window/monitor, so cover it via the native-call seam or treat it as
  owner-verified (it is byte-for-byte the pre-existing code).
- Vitest: no new web tests required (the runtime is unchanged) — just confirm the existing suite stays
  green and that `monitorProjection.ts`/`host.ts` were not edited.
- Manual (dev): launch `--simulator`, load the 10.1 fixtures (e.g. the reproduced `SIM_MONITORS`),
  eyeball that viewports lay out as the virtual desktop with the correct edge-glow spill direction per
  monitor; swap a scenario and confirm live re-layout without restart; reassign a per-monitor effect.

### Out of scope
- Content sources beyond what 10.1 provides (media-file decode, mirroring a real monitor) — Story 10.3.
- RGB peripheral and audio visualization in the composite — Story 10.4.
- The interactive topology editor, scenario library, and headless render/automation hook — Story 10.5.
- True OS-level placement/DPI/capture fidelity (the Indirect Display Driver path) — declined for this
  epic; the composite *approximates* per-monitor DPI and bypasses WGC for synthetic frames.
- Any change to `WindowConfigPayload`, the bridge, `EngineCoordinator`, `MonitorLayout`, or the effect
  runtime. The seam is the surface factory and the two new sim-only classes; nothing else moves.
