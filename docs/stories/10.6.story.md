# Story 10.6: Simulator Usability — Launcher, Linked-Window Shutdown, Readable Controls & a Pannable Canvas

## Status
Ready for Review

## Story
**As a** developer/QA using the Layout Simulator,
**I want** a one-double-click way to launch it, a session whose two windows close together instead of
stranding one, editor controls I can actually read, and a virtual-desktop canvas I can pan and zoom
while the settings stay put,
**so that** the simulator is quick to start and comfortable to drive day-to-day — without changing any
of the real pipeline it tests or anything in the shipped product.

## Context
Epic 10 stories 10.1–10.5 built the simulator and shipped it green: simulated topology/capture (10.1),
the composite `SimulatorWindow` of scaled viewports (10.2), media/mirror content (10.3), RGB + audio
readback (10.4), and the interactive `SimulatorEditorPanel` + scenario library + headless render hook
(10.5). It works — but using it has rough edges that this story files down. All four are pure
**dev/QA ergonomics**; none touch the fidelity invariant, the bridge, or the signed build.

1. **Launching is fiddly.** Today you must produce a Debug build and start it with the `--simulator`
   arg or set `AMBIENTFX_SIMULATOR=1` (`App.xaml.cs:210-211`). There is no friendly entry point —
   every launch is a terminal incantation.
2. **The two windows aren't linked.** In simulator mode the app is still tray-first
   (`App.xaml:4` `ShutdownMode="OnExplicitShutdown"`), so you get the normal `ControlWindow` **and** the
   `SimulatorWindow`. Closing the `SimulatorWindow` does nothing to the process (explicit-shutdown), and
   closing the `ControlWindow` only hides it to the tray (`ControlWindow.OnClosing` cancels the close and
   raises `CloseRequested`, `ControlWindow.cs:159-165`). So you exit one window and are left with an
   orphan window and/or a tray process still running.
3. **Editor controls are unreadable.** The non-accent buttons set `Background = null`
   (`SimulatorEditorPanel.cs:406`), so they render with no fill and the default near-black text on the
   dark panel (`0xE0,0x16,0x16,0x1c`) — black-on-dark, unreadable. The monitor `ListBox` has the mirror
   problem: light `Gainsboro` item text (`SimulatorEditorPanel.cs:336`) on the control's default **white**
   background. The owner reported "settings on the buttons I can't read — they're all black."
4. **The canvas only auto-fits — you can't get closer.** `Reflow()` (`SimulatorWindow.cs:210-270`)
   computes a single uniform scale + centering offset that fits the whole virtual desktop into the
   window every time. There is no way to pan around or zoom into a region (e.g. inspect one edge's glow
   on a 6-monitor wall); a dense layout is rendered tiny with no recourse.

Like all of Epic 10, every line of this story lives behind the dev-only gate from 10.1
(`#if SIMULATOR_ENABLED` + the `--simulator` / `AMBIENTFX_SIMULATOR` runtime gate) and is stripped from
the signed Velopack build. The launcher script is the one new artifact that lives outside the
`#if`-guarded tree (it is just a build+run wrapper) but it only ever produces a **Debug** run, so it
cannot start a simulator that a Release build doesn't contain.

## Acceptance Criteria
1. **One-double-click launcher (owner choice: launcher script).** A repo-root script
   (`run-simulator.ps1`, with a thin `run-simulator.cmd` shim so it is double-clickable from Explorer
   without a "run with PowerShell" detour) builds the **Debug** engine and starts it with `--simulator`,
   requiring no manually typed arguments or env vars. It:
   - Builds (or, if `-NoBuild`/already-built, reuses) the Debug `AmbientFx.exe` and launches it with
     `--simulator`; surfaces build failures clearly instead of silently launching a stale binary.
   - Optionally forwards a scenario name to preselect (e.g. `run-simulator.ps1 six-grid`), but defaults
     to the existing default scenario when none is given.
   - Lives alongside the existing `build.ps1` and is documented in `docs/SIMULATOR.md`'s **Launch**
     section as the recommended way to start the tool (the `--simulator` arg / `AMBIENTFX_SIMULATOR`
     env remain documented as the underlying mechanism).
2. **Linked-window shutdown (owner choice: close both & exit).** While in simulator mode, closing
   **either** the `SimulatorWindow` **or** the `ControlWindow` cleanly shuts the **whole** simulator
   session down (engine `ShutdownAsync`, DI dispose, log flush, tray icon removed) via
   `Application.Current.Shutdown()` — no orphan window, no lingering tray process. Specifically:
   - Closing the `SimulatorWindow` triggers application shutdown (it does nothing today).
   - In simulator mode, closing the `ControlWindow` shuts the app down rather than hiding to the tray
     (the production tray-first behavior at `ControlWindow.cs:159-165` is unchanged for normal runs;
     the override is gated to simulator mode only).
   - Shutdown is idempotent/guarded so the first window to close wins and the second closing as a
     consequence does not double-shutdown or throw.
   - **Production behavior is untouched:** a non-simulator run remains tray-first with
     `ShutdownMode="OnExplicitShutdown"`; closing the control window still hides to tray.
3. **Readable editor controls (owner choice: full dark-theme pass).** Every interactive control in the
   `SimulatorEditorPanel` is legible against the dark panel: buttons (non-accent and accent), the
   scenario/source/content **dropdowns**, the monitor **list**, the **text boxes**, and **checkbox**
   labels all use a consistent readable light-on-dark styling with sufficient contrast in normal, hover,
   focused, selected, and disabled states. No control renders as black-on-dark or light-on-light. The
   accent ("Simulate display change") button stays visually distinct.
4. **Pannable + zoomable canvas with the settings fixed (owner choice: pan + zoom + Fit reset).** The
   virtual-desktop view in `SimulatorWindow` can be:
   - **Panned** by dragging an empty area of the canvas (background), moving the whole monitor
     arrangement — including effect viewports, backdrops, and the RGB peripheral layer — together.
   - **Zoomed** with the mouse wheel, ideally centered on the cursor; zoom has sane min/max clamps.
   - **Reset** by a **Fit** control that restores the current auto-fit-to-window scale and centering
     (today's `Reflow()` behavior) and clears any pan offset.
   - The **editor panel and the ceiling/warning text stay fixed** in place (screen-anchored) regardless
     of pan/zoom — only the monitor canvas transforms. Pan/zoom re-derives viewport geometry such that
     the WebView2 effect surfaces remain correctly placed and sized (see Dev Notes — fold pan/zoom into
     the existing scale/offset math, do **not** rely on a WPF `RenderTransform` over windowed WebView2).
5. **Fidelity invariant honored.** None of the above forks or alters the real pipeline
   (`EngineCoordinator`, `MonitorLayout.ComputeRelation`, `monitorProjection.ts`, the effect runtime,
   `LedProjection`, `AudioModulation`) and there is **no bridge-contract change**. The viewports still
   receive the real `WindowConfigPayload`; pan/zoom is presentation-only (canvas scaling/offset, already
   the single sanctioned adaptation from 10.2). The editor still only mutates inputs and triggers
   existing seams.
6. **Dev-only & green.** All UI/wiring sits behind the 10.1 gate and is absent from the signed
   Release/Velopack build (no new simulator IL ships; zero Free/Premium/licensing/packaging impact); the
   launcher script only ever starts a Debug build. Existing xUnit + Vitest suites stay green; this story
   adds the focused coverage in AC-tests below. `docs/SIMULATOR.md` is updated for the launcher,
   linked-window shutdown, and the pan/zoom/Fit controls.
7. **Drag-to-arrange monitors (Windows-style) + easy add (owner follow-up).** The composite window can
   reposition monitors by direct manipulation, like the Windows "Display arrangement" screen:
   - An **Arrange** toggle in a screen-fixed toolbar. While on, the live effect surfaces are hidden (a
     *windowed* WebView2 can't be grabbed or drawn through — airspace), and each monitor becomes a
     draggable box; while off, the live composite shows as before.
   - **Dragging** a box updates the real topology live, with **edge-snapping** to neighbors (adjacency
     and alignment) so flush layouts (3-wide / L-shape / stack) build quickly; negative coords and gaps
     are preserved. The view does not re-fit mid-drag (the mapping is captured at mouse-down), then
     re-fits on drop. Selecting/dragging a box syncs the Layout Editor's selection and X/Y fields.
   - An **+ Add monitor** toolbar button adds a monitor (shared id scheme with the editor's Add) and
     selects it for dragging.
   - On exiting Arrange, the engine re-syncs once to the arranged layout
     (`SimulatedMonitorDetectionService.FireMonitorsChanged`) and the live effects return. Drag/add only
     mutate inputs and trigger the existing seams — no pipeline/bridge change (fidelity invariant). The
     snap math is pure (`SimulatorLayoutMath.Snap`) and unit-tested.
8. **Feed the source real content — picture / video / mirror (owner follow-up).** The source monitor can
   be driven by real content so effects are judged on realistic input, not just test patterns:
   - **Picture** (PNG/JPG/BMP/GIF or an image-folder sequence) — already supported by Story 10.3's
     `MediaContentSource` (in-box WIC).
   - **Video** (MP4/MOV/AVI/WMV/MKV/WEBM) — **new**: a `VideoContentSource` plays the file via the in-box
     WPF `MediaPlayer` (Windows Media Foundation codecs) on its own dispatcher thread and publishes frames
     to the capture seam, looping. **No new native dependency** (ffmpeg/OpenCvSharp still avoided).
     NFR5-safe (missing file / bad codec → blank + one-shot error, never throws). The "media" kind
     auto-routes image vs video by extension (`SimMediaKinds`).
   - **Mirror your monitor** — already supported (`MirrorContentSource`, real WGC); now pickable from a
     **dropdown of real displays** instead of typing a `\\.\DISPLAY` id.
   - **Easy + onto the source:** a **Browse picture/video…** file picker and the mirror dropdown apply in
     one click to the **engine source** monitor (and set it as source) so the content immediately drives
     the effect; an "apply to selected monitor" path remains for composite context. Fidelity invariant
     upheld (content flows through the unchanged capture seam; single-source behavior unchanged).

## Dev Notes

### Scope: this is ergonomics, not engine work
All four asks are UI/launch conveniences over the existing simulator. The hard parts (real engine
against fabricated topology, the surface seam, RGB/audio readback) are done in 10.1–10.4; the shell is
10.5. This story does **not** add capability to the pipeline under test — keep that framing to avoid
scope creep into "while I'm here" engine changes. [Source: docs/stories/epic-10-layout-simulator.md:94-101]

### The fidelity invariant still rules (state and uphold it)
The simulator must reuse the real pipeline **unmodified** — `EngineCoordinator`
(`src/Engine/Services/EngineCoordinator.cs`), `MonitorLayout.ComputeRelation`
(`src/Engine/Services/MonitorLayout.cs`), `web/src/effects/shared/monitorProjection.ts`, the effect
runtime, `LedProjection`, `AudioModulation` — with **no bridge-contract change**. Pan/zoom is exactly
the kind of presentation-only adaptation 10.2 already sanctions ("canvas scaling is the only
adaptation"): the surfaces keep getting the **real** `WindowConfigPayload` from
`EngineCoordinator.BuildWindowConfigFor`; we only change where/at-what-scale they are drawn in the
composite. If a surface ever read a fabricated payload, the test would no longer be valid.
[Source: docs/stories/epic-10-layout-simulator.md:48-53, 132-134, 176-186; docs/SIMULATOR.md:136-144]

### AC1 — launcher script (precedent + the Debug gate)
- `build.ps1` already lives at the repo root and is the precedent for a top-level dev script; mirror its
  style. The Release publish there is `-c Release` (`build.ps1` ~lines 76-82), which defines **no**
  `SIMULATOR_ENABLED`, so the simulator IL is stripped. The launcher must therefore hard-code
  `-c Debug` — that is the *only* config where `SIMULATOR_ENABLED` is defined
  (`AmbientFx.csproj:27-29`). [Source: src/Engine/AmbientFx.csproj:23-29]
- The runtime gate the script ultimately trips is the existing `IsSimulatorRequested`
  (`App.xaml.cs:208-211`) — `--simulator` or `AMBIENTFX_SIMULATOR`. The script just supplies `--simulator`
  so the developer doesn't have to. Forward an optional scenario name; today the default scenario is
  loaded by `SimulatorScenario.LoadDefault` (`SimulatorComposition.cs:34-35`) — if a scenario arg is
  passed, route it the same way the editor's library load does (`SimulatorScenarioLibrary.Load`) or set
  the default-scenario env/arg the composition reads (keep it minimal; preselecting is a nicety, not the
  core AC). [Source: src/Engine/App.xaml.cs:202-211; src/Engine/Simulator/SimulatorComposition.cs:34-35]

### AC2 — linked-window shutdown (the two real obstacles)
The app is **tray-first**: `App.xaml:4` sets `ShutdownMode="OnExplicitShutdown"` and there is no
`StartupUri` — so closing windows never ends the process by itself; only `Application.Current.Shutdown()`
(routed through `App.OnExit`, `App.xaml.cs:113-144`) does. Two things must change **in simulator mode
only**:
1. **`SimulatorWindow` close → shutdown.** It has no close handler today
   (`SimulatorWindow.cs:30-80`); add an `OnClosing`/`Closed` that calls
   `Application.Current.Shutdown()`.
2. **`ControlWindow` close → shutdown (sim mode).** Production intercepts the close and **hides to
   tray**: `OnClosing` sets `e.Cancel = true` and raises `CloseRequested` unless `_forceClosing`
   (`ControlWindow.cs:159-165`); there is already a `ForceClose()` (`:151-155`) that really closes. In
   simulator mode, a user close should end the session. Prefer a dev-only opt-in (e.g. a
   `SimulatorMode` flag on `ControlWindow`, or have the simulator subscribe to `CloseRequested` and call
   `Application.Current.Shutdown()`/`ForceClose()`) set during `SimulatorComposition.Apply` — so the
   production path (`:159-165`) is byte-for-byte unchanged for normal runs.
- **Idempotency:** the first close shuts down; the engine teardown closes/disposes everything, which may
  fire the second window's close handler. Guard with a single `_shuttingDown` flag (and/or check
  `Application.Current` is already shutting down) so shutdown runs once. `App.OnExit` already does the
  real teardown (coordinator `ShutdownAsync`, provider dispose, log flush, mutex release) —
  don't duplicate it; just trigger it.
[Source: src/Engine/App.xaml:4; src/Engine/App.xaml.cs:113-144; src/Engine/Hosting/ControlWindow.cs:150-165]

### AC3 — readability (why it's black, and the fix)
- **Buttons:** `Btn(...)` sets `Background = accent ? blue : null` and `Foreground = accent ? White :
  null` (`SimulatorEditorPanel.cs:398-411`). Setting `Background = null` (vs. leaving the default) makes
  the non-accent buttons render with no fill, so the dark panel (`0xE0,0x16,0x16,0x1c`,
  `SimulatorEditorPanel.cs:69`) shows through and the inherited near-black text is invisible. Give
  non-accent buttons an explicit dark-grey fill + light foreground (and proper hover/pressed/disabled).
- **Monitor list:** `ListBoxItem`s are `Foreground = Gainsboro` (`:336`) on the `ListBox`'s default
  **white** background (`:40`) — light-on-light. Style the `ListBox` dark with light item text and a
  readable selection highlight.
- **Dropdowns/text/checkbox:** `_library/_source/_contentKind` ComboBoxes, the `NumBox()` TextBoxes
  (`:379`), `_fps/_effect/_contentArg`, and the `_primary` CheckBox label all currently rely on default
  (light) chrome; bring them into the dark theme too (AC3 = "all editor controls"). Note the panel sits
  on the dark `SimulatorWindow` background (`SimulatorWindow.cs:59`), so light-on-dark is the target
  everywhere.
- Define the styling **once** (shared brushes or a tiny `ResourceDictionary` scoped to the panel) so it
  is consistent and new controls inherit it. This is pure WPF styling — no behavior change, no new
  dependency.
[Source: src/Engine/Simulator/SimulatorEditorPanel.cs:40, 45-51, 69, 326-411; SimulatorWindow.cs:59]

### AC4 — pan/zoom without breaking WebView2 placement
`Reflow()` (`SimulatorWindow.cs:210-270`) computes one auto-fit `scale` and centering `offsetX/offsetY`
from the monitors' bounding box and the canvas size, then `Canvas.SetLeft/Top` + sets `Width/Height` for
each backdrop and each `SimulatorEffectSurface`, and finally lays out the peripheral layer relative to
the source rect. **Fold pan/zoom into this same math** rather than transforming the canvas:
- Keep computing the auto-fit base scale; the **effective** scale = base × `_userZoom`; the **effective**
  offset = centering offset + (`_panX`, `_panY`).
- Re-run `Place(...)` for every element with the effective scale/offset; the peripheral `Layout(srcRect)`
  uses the same effective srcRect. This guarantees the windowed WebView2 surfaces get real
  `Canvas.SetLeft/Top`/`Width`/`Height` (which they honor) instead of a WPF `RenderTransform` (which
  windowed/airspace WebView2 does **not** reliably honor for hit-testing/placement).
- **Fit** = `_userZoom = 1`, `_panX = _panY = 0`, then `Reflow()` (the existing auto-fit).
- Wheel-zoom about the cursor: adjust `_panX/_panY` so the world point under the cursor stays under the
  cursor as scale changes (standard zoom-to-cursor; compute from `e.GetPosition(_canvas)`).
- Pan must start only on **empty canvas background** hits, not on a viewport/backdrop — otherwise it
  fights the 10.5 viewport-drag (if that drag exists in the build). Use the canvas itself (not a child)
  as the drag source and check the hit target.
- The editor panel and `_warning` live in the **root `Grid`**, not the `_canvas`
  (`SimulatorWindow.cs:74-77`, `ConfigureEditor` adds the editor to the Grid at `:158-161`), so they are
  already screen-fixed and must stay that way — apply pan/zoom only to `_canvas` content.
[Source: src/Engine/Simulator/SimulatorWindow.cs:62-80, 147-162, 209-270]

### Gating & shipping (unchanged from 10.1)
All window/editor changes sit behind `#if SIMULATOR_ENABLED` (defined only in the Debug configuration's
`DefineConstants`, `AmbientFx.csproj:27-29`) plus the runtime `--simulator` / `AMBIENTFX_SIMULATOR` gate
(`App.xaml.cs:208-211`). The `ControlWindow` change must be gated so the production close path is
unchanged in Release. The launcher script lives outside the `#if` tree (it's a build wrapper) but only
ever produces a Debug `--simulator` run, so it can't surface a simulator that Release doesn't contain.
The Release publish in `build.ps1` strips Debug-only constants → no simulator IL, zero
Free/Premium/licensing/packaging impact. [Source: src/Engine/AmbientFx.csproj:23-29; src/Engine/App.xaml.cs:202-211; docs/stories/epic-10-layout-simulator.md:90-92, 176-178]

### Testing
- **xUnit** is the workhorse (no WebView2/GPU dependency where avoidable):
  - Pan/zoom geometry: if needed, extract the pure scale/offset→rect computation from `Reflow` into a
    small testable function; assert Fit == today's auto-fit rects, pan translates all rects equally, and
    zoom scales about the anchor. [Source: src/Engine/Simulator/SimulatorWindow.cs:209-270]
  - Linked-shutdown idempotency: assert the `_shuttingDown` guard makes a second close a no-op.
  - Keep these off real-hardware / real-WGC paths (NFR5: never throws).
- **Vitest:** no bridge-contract change is expected (AC5), so web tests need no new coverage; keep them
  green.
- **Manual (dev/QA):** double-click `run-simulator.cmd`; confirm it builds Debug and opens the simulator;
  close the simulator window → app exits; relaunch, close the control window → app exits (no orphan, no
  tray remnant); read every editor control comfortably; drag to pan, wheel to zoom, hit Fit to reset;
  confirm the editor panel and warning stay put. The simulator still does **not** replace owner
  verification on real extra monitors. [Source: docs/SIMULATOR.md:115-134]

### Out of scope
- **Any production-UI change.** The linked-shutdown override and all styling are dev-only; the shipped
  `ControlWindow` tray-first behavior and the Free/Premium UI are untouched.
  [Source: docs/stories/epic-10-layout-simulator.md:176-178]
- **Engine/pipeline changes, new content sources, new RGB/audio behavior.** This is ergonomics over the
  existing simulator only.
- **A full in-app launcher button / VS profile / desktop shortcut.** The owner chose the launcher-script
  route for this story; the other launch mechanisms were considered and deferred (the script + the
  existing `--simulator`/env gate suffice).
- **Persisting pan/zoom or window layout across runs.** Pan/zoom is session-only; Fit restores the
  auto-fit. (The simulator already never persists to `settings.json` —
  [Source: docs/SIMULATOR.md:24-27].)
- **Indirect Display Driver path / real-hardware fidelity / full CI golden-image suite** — remain out of
  scope per the epic. [Source: docs/stories/epic-10-layout-simulator.md:188-194]
