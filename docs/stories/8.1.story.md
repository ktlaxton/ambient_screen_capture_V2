# Story 8.1: Position-Mapped RGB Peripheral Output

## Status
Done — implemented, tested, and owner-verified on hardware 2026-06-12.

## Story
**As a** user with Corsair RGB hardware on my desk,
**I want** my keyboard, mouse, light strips and other peripherals to glow with the matching edge of
my screen,
**so that** the ambient effect spills off the monitor onto real hardware — a desk-wide Ambilight,
not just a multi-monitor one.

## Context
The engine already computes `FramePayload.Edges` (`EdgeColors` — top/bottom/left/right sRGB zone
strips) every frame and fans it out to the effect windows via
`EngineCoordinator.OnFrameReady → _windowManager.PostToAll` (`EngineCoordinator.cs:816`). This story
adds a **parallel consumer**: an ambient-device service that maps those same zones onto physical LED
positions and drives them through **RGB.NET** (`RGB.NET.Devices.Corsair`, which wraps the iCUE SDK).
No capture/processing changes. The spatial mapping mirrors the philosophy of `MonitorLayout`
(Story 7.5): an LED at a given `(x,y)` is fed by the screen edge/zone it physically aligns with.

## Acceptance Criteria
1. **Connect & discover.** On enable, the service initializes RGB.NET with the Corsair provider,
   connects to a running iCUE, and enumerates devices with their per-LED positions. The connection
   is asynchronous and **never blocks or crashes the host** (NFR5) — matching the capture/audio
   services' defensive posture.
2. **Graceful unavailability.** If iCUE is not installed, not running, third-party control is
   disabled, or no supported devices are present, the feature degrades cleanly: a clear status
   message (info/warn toast + UI state), the rest of the app fully functional, no exceptions
   surfaced to the user. Re-checking/reconnecting works without an app restart (RGB.NET auto-reconnect
   or an explicit retry).
3. **Position-mapped output.** Each device's LEDs are colored by projecting their normalized
   `(x,y)` positions onto the edge zones of the source screen: an LED on the left of the device →
   the source's left edge zone at the matching height, etc. The mapping is a **pure, unit-tested
   helper** (e.g. `AmbientFx.Devices.LedProjection`), independent of RGB.NET types, reusable across
   vendors. Light strips/fans (logical-unit coordinates) and keyboards/mice (mm coordinates) are
   each normalized to 0..1 per device before projection.
4. **Sane update rate.** Colors are pushed through RGB.NET's own update mechanism, **rate-limited**
   well below the capture FPS (e.g. ~30 Hz or RGB.NET's default update trigger) so hardware isn't
   flooded. The frame handler is non-blocking and thread-safe (it runs on the processing background
   thread — see `OnFrameReady`).
5. **Release on shutdown / disable.** On app exit or when the feature is turned off, the service
   releases lighting control back to iCUE so the user's normal profiles resume (no LEDs left frozen
   on the last frame). This is wired into the existing enable/disable (`ApplyEnabledState`) and
   shutdown paths (Story 7.3).
6. **Master controls + device list in the UI.** The control window gains: an **enable toggle** for
   ambient peripherals, a **peripheral brightness** control, and a **read-only device list** showing
   discovered devices and the live connection state (connected / iCUE not found / control refused /
   no devices). Auto-mapping only — no per-device manual placement yet (deferred to 8.2).
7. **Persistence + bridge contract.** New settings (at least `AmbientDevicesEnabled`,
   `PeripheralBrightness`) persist via `ApplicationSettings`/`SettingsService`, are mirrored in
   `web/src/shared/bridge.ts`, apply live, and are forward/back compatible (unknown keys ignored,
   missing keys default — the Story 7.2/SettingsService pattern). Device state pushed to the UI uses
   a new engine→web message (e.g. `devices`) mirrored on both sides.
8. **Lifecycle & DI.** The service is a DI singleton (`App.xaml.cs:171-181`), constructed and wired
   in `EngineCoordinator` alongside the other pipeline services, started/stopped with enabled state,
   and disposed on shutdown. It must be safe to construct even when RGB.NET/iCUE is entirely absent.
9. **Tests green & extended.** xUnit covers the projection math (corner cases like an LED dead-center,
   off-axis, normalization of mm vs logical units) and the service lifecycle with a **mocked device
   provider** (no real hardware in CI). Vitest covers the new settings/device-list bridge plumbing.
   Existing suites stay green.
10. **Real-hardware verification.** Manually verified on the owner's Corsair hardware with iCUE
    running: devices light with screen-edge colors, disabling restores iCUE's profile, and quitting
    leaves no frozen LEDs. (Owner-run; recorded in QA Results.)

## Dev Notes

### The data is already produced — this is a new sink, not a new source
[Source: `src/Engine/Bridge/EngineMessages.cs:25-46`, `EngineCoordinator.cs:816`]
- `FramePayload.Edges` = `EdgeColors { Top, Bottom, Left, Right : int[][] }`, sRGB 0-255, length =
  `ZonesPerEdge`. Top/bottom run left→right; left/right run top→bottom (same as the web effects and
  the `MonitorLayout`/Story 7.5 conventions).
- `OnFrameReady` runs on the **processing background thread**; `PostToAll` is thread-safe. The new
  consumer must likewise be non-blocking and thread-safe, and must not throw back into the pipeline
  (the existing handler has no try/catch around `PostToAll` because Post* is safe — keep the device
  push equally safe or wrap it).

### Service lifecycle to mirror
[Source: `EngineCoordinator.cs:222-260`, `App.xaml.cs:171-181`]
- Register as a DI singleton next to `IScreenCaptureService` etc.; inject into `EngineCoordinator`,
  wire events in `StartAsync`, start in `ApplyEnabledState` (enabled + valid source), stop/release in
  `StopPipeline` and on shutdown. Wrap start/stop in try/catch + log, exactly like
  `StopPipeline` does for capture/audio.

### Spatial mapping — reuse the Story 7.5 mental model
[Source: `src/Engine/Services/MonitorLayout.cs`, `web/src/effects/shared/monitorProjection.ts`]
- 7.5 projected a target *monitor's* edge span onto the *source* edge. Here the analog is: project a
  device LED's normalized position onto the nearest source edge zone (and blend toward the interior
  / dominant color as the LED sits further from any edge). Keep the helper pure and table-tested like
  `MonitorLayoutTests` so it needs no hardware.

### RGB.NET specifics to confirm during implementation
- Surface API differs from the raw iCUE C API: RGB.NET exposes `RGBSurface`, device providers,
  `Led` objects with `Location`, and an update loop (`RGBSurface.Update()` / update triggers). Push
  colors by setting `Led.Color` and triggering an update — don't call a raw `CorsairSetLedColors`.
- Use a rate-limited update trigger (RGB.NET ships timer-based triggers) so hardware updates ≈30 Hz
  regardless of capture FPS (AC4).
- Releasing control: detach/dispose the Corsair provider / surface so iCUE resumes its own profiles
  (AC5). Verify the exact call on real hardware — this is a known fiddly area.
- Coordinate spaces: keyboards/mice report mm, strips/fans report logical units; normalize each
  device's LED bounding box to 0..1 before projection (AC3).

### Compatibility / risk
- **iCUE must be running**; treat absence as a normal state, not an error (AC2). The owner has iCUE +
  hardware, so AC10 verification is real.
- **LGPL-2.1**: keep RGB.NET unmodified and dynamically linked (NuGet), document it; flag for the 7.4
  installer review (tracked as Epic 8 guardrail / story 8.4).

### Testing
- xUnit for the projection math and the service (mocked provider — **no hardware in CI**). The
  service must be unit-constructable with the provider abstracted behind an interface so tests don't
  load native iCUE bits.
- Vitest for the settings/device-list bridge plumbing.
- Manual owner pass for the on-hardware behaviors that can't be unit-tested (AC10).

### Completion Notes List
- **Native SDK discovery:** `RGB.NET.Devices.Corsair` 3.2.0 ships managed assemblies only;
  the iCUE SDK native client must be deployed by the app. Pulled the official redist
  (`iCUESDK.x64_2019.dll`, v4.0.84) from CorsairOfficial/cue-sdk and committed it under
  `src/Engine/native/x64/`; the backend also prepends the absolute output path to
  `CorsairDeviceProvider.PossibleX64NativePaths` so discovery is CWD-independent.
- **Provider singleton:** `CorsairDeviceProvider` allows one live instance, but `Dispose`
  clears the singleton — so the service creates one backend (provider+surface) per
  enable-session and disposes it on stop, which both releases control to iCUE (AC5) and
  makes off/on retry work (AC2).
- **Rate limiting** is a service-owned 33 ms timer calling `RGBSurface.Update()` manually
  (no RGB.NET update trigger registered): unchanged frames are skipped (reference compare),
  overlapping ticks are dropped via an `Interlocked` guard, and a brightness change forces a
  re-push of the latest frame. Equivalent to AC4's "~30 Hz" intent with a simpler seam.
- **Connect timeout** raised from RGB.NET's 500 ms default to 5 s (iCUE can be slow to
  accept sessions right after startup).
- Devices run only while the pipeline runs (master enabled + valid source) AND
  `AmbientDevicesEnabled` — frames are the only color source, so a standalone device session
  would just freeze on the last frame.
- AC10 (owner hardware pass) is the only open item; everything else is unit/integration
  covered (283 xUnit + 258 Vitest green).
