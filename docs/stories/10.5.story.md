# Story 10.5: Topology Editor, Scenario Library & Automation Hooks

## Status
Ready for Review

## Story
**As a** developer/QA,
**I want** to author and save monitor layouts interactively, replay a curated library of standard
arrangements, and expose a headless render hook that runs a scenario through the real engine and
captures a deterministic image artifact,
**so that** I can sweep every display configuration the product must support on a 2-monitor machine
and seed a future automated snapshot-regression suite — all without touching the shipped product.

## Context
Stories 10.1–10.4 build the simulator's machinery: `SimulatedMonitorDetectionService` /
`SimulatedScreenCaptureService` and the JSON scenario fixture format (10.1), the composite
`SimulatorWindow` of scaled per-monitor viewports running the real effect runtime (10.2), media-file
and mirror content sources (10.3), and the `VisualizationBackend` RGB readback plus
`SimulatedAudioCaptureService` (10.4). What is missing is the **shell** that ties them together for a
human: a way to build a topology by hand, flip through a named library of the layouts the product is
supposed to support, and drive the "simulate display change" path on demand.

This story is that interactive shell, plus two seams that point forward: a curated scenario library so
QA isn't hand-typing rects, and a **headless render hook** — a code path that takes a scenario fixture,
runs the engine, and writes the composite (or per-surface) output to image file(s). That hook is the
exact seam a future CI golden-image suite would diff; building the full CI suite is **out of scope**
(Epic 10 "Out of scope"), but proving the hook produces a *deterministic* artifact for at least one
scenario is in scope. The story also delivers `docs/SIMULATOR.md`, the dev doc that explains how to run
and edit all of this and — critically — what fidelity the simulator does and does not give you.

Like all of Epic 10, every line of this story lives behind the dev-only gate from 10.1
(`#if SIMULATOR_ENABLED` + the `--simulator` / `AMBIENTFX_SIMULATOR` runtime gate) and is stripped from
the signed Velopack build.

## Acceptance Criteria
1. **Interactive topology editor.** Within the simulator shell (dev-only) the user can build and mutate
   a topology live, with no app restart:
   - Add and remove virtual monitors (1–6 supported, matching the 10.2 ceiling).
   - Set each monitor's **position** by dragging its viewport in a mini virtual-desktop map **and** by
     typing exact X/Y; negative coordinates and gaps are allowed and preserved.
   - Set **resolution** (width/height), **orientation** (portrait/landscape — modeled as `width < height`
     per the existing `MonitorInfo` convention, no new rotation field unless a test demands one),
     **DPI/scale** (a per-monitor scale factor stored in the fixture, applied as virtual-desktop pixel
     bounds — see Dev Notes), and which monitor is **primary** (exactly one).
   - Pick the engine **source** monitor and assign a **per-monitor effect** and the global **FPS**
     (`maxFps`), reusing the existing settings/effect-assignment plumbing.
2. **"Simulate display change" button.** A control fires `SimulatedMonitorDetectionService`'s
   on-demand `MonitorsChanged` (10.1) after a mutation, exercising hot-plug (add), unplug (remove),
   resolution change, and orientation change through the **real**
   `EngineCoordinator` re-sync path (`HandleMonitorsChangedOnUi`, `EngineCoordinator.cs:1119-1145`) with
   the effect running. Removing the current source display drives the real source-lost path.
3. **Curated named scenario library.** A set of named, ready-to-load JSON scenario fixtures ships with
   the simulator (dev-only resources), at minimum:
   `SIM_MONITORS` (reproducing `web/src/shared/simulator.ts:33-37` exactly: DISPLAY1 "Primary 1440p"
   2560×1440 @ (0,0) primary; DISPLAY2 "Right 1080p" 1920×1080 @ (2560,180); DISPLAY3 "Top 1080p"
   1920×1080 @ (320,-1080)), plus **3-wide**, **L-shape**, **vertical stack**, **portrait-flanked**
   (a `width<height` monitor beside a landscape one), **mixed-DPI**, **gapped**, and a **dense 6-monitor
   grid**. Each loads into the editor in one action.
4. **Save / load custom scenarios.** A topology authored in the editor can be saved to a JSON scenario
   file (the 10.1 fixture schema) and loaded back, round-tripping every field in AC1 with no loss. Saved
   fixtures are interchangeable with the curated library and with the automation hook (AC5).
5. **Headless render / automation hook.** A headless entry point accepts a scenario fixture, runs the
   **real** engine end-to-end against it (no manual interaction), and renders/captures the composite
   (and/or per-surface) output to image file(s) on disk. For determinism it uses a **fixed synthetic
   content pattern at a fixed frame index/seed** (not wall-clock time). For ≥1 curated scenario the hook
   produces a **byte-stable artifact** across repeated runs on the same machine. The hook is reachable
   both programmatically (for a future test) and from the dev gate (e.g. a `--simulator-render <scenario>`
   sub-mode). Building the full CI golden-image diff suite is **out of scope**.
6. **`docs/SIMULATOR.md`.** A dev doc covers: how to launch (`--simulator` / `AMBIENTFX_SIMULATOR`),
   editing topologies, the curated scenario library, content sources (synthetic/media/mirror), the
   RGB/audio visualization, the automation hook, and an explicit **Known fidelity limitations** section
   (synthetic/media bypass real WGC; viewports approximate real OS placement & per-monitor-V2 DPI; only
   "mirror" exercises real capture; the tool is **not** a substitute for real-hardware verification; IDD
   remains the documented future full-fidelity option).
7. **Fidelity invariant honored.** The editor, library, and hook reuse the real pipeline
   (`EngineCoordinator`, `MonitorLayout.ComputeRelation`, `monitorProjection.ts`, the effect runtime,
   `LedProjection`, `AudioModulation`) **unmodified** — no forking of projection/effect/LED/audio logic
   and **no bridge-contract change**. Canvas scaling is the only adaptation allowed.
8. **Dev-only & green.** All of the above sits behind the 10.1 gate and is absent from the signed
   Release/Velopack build (no simulator IL; zero Free/Premium/licensing/packaging impact). Existing xUnit
   + Vitest suites stay green; this story adds: scenario-fixture load/validate tests, and a test asserting
   the headless render hook produces a deterministic artifact for one scenario.

## Dev Notes

### Where this sits relative to 10.1–10.4 (all sibling drafts, not yet implemented)
This story is the interactive shell + curated fixtures + the future-automation seam + the dev doc. It
**depends on** and assembles the other four:
- 10.1 defines the JSON scenario fixture schema, `SimulatedMonitorDetectionService` (with on-demand
  `MonitorsChanged`), `SimulatedScreenCaptureService`, and the `SIMULATOR_ENABLED` + `--simulator` /
  `AMBIENTFX_SIMULATOR` gate. This story consumes that schema and that fire-on-demand seam directly.
  [Source: docs/stories/epic-10-layout-simulator.md:103-119]
- 10.2 builds the composite `SimulatorWindow` of scaled viewports + the `IEffectSurfaceHost` seam; the
  editor manipulates *that* canvas (drag = move a viewport). [Source: docs/stories/epic-10-layout-simulator.md:121-134]
- 10.3 adds media/mirror content sources; the editor's source picker assigns them per monitor.
  [Source: docs/stories/epic-10-layout-simulator.md:136-145]
- 10.4 adds the `VisualizationBackend` RGB readback and `SimulatedAudioCaptureService`; the editor
  toggles/visualizes them. [Source: docs/stories/epic-10-layout-simulator.md:147-159]
The 10.x story files do not exist yet (only the epic). Reference them by epic section, not by file path.

### The fidelity invariant (state and uphold it)
The simulator must reuse the real pipeline **unmodified**: `EngineCoordinator`
(`src/Engine/Services/EngineCoordinator.cs`), `MonitorLayout.ComputeRelation`
(`src/Engine/Services/MonitorLayout.cs`), `web/src/effects/shared/monitorProjection.ts`, the effect
runtime, `LedProjection` (`src/Engine/Devices/LedProjection.cs`), and `AudioModulation`
(`src/Engine/Devices/AudioModulation.cs`). **No fork** of projection/effect/LED/audio logic, and **no
bridge-contract change** (`src/Engine/Bridge/` ↔ `web/src/shared/bridge.ts`). Canvas scaling (10.2) is
the only adaptation allowed. The editor only *mutates inputs* (the topology + settings) and *triggers*
the existing seams; it never reimplements pipeline behavior.
[Source: docs/stories/epic-10-layout-simulator.md:48-53, 176-186]

### The scenario fixture is the contract everything shares
The editor mutates a fixture, the library is a set of fixtures, save/load serializes a fixture, and the
headless hook consumes a fixture — one schema (defined in 10.1) throughout. A fixture describes a
topology: per-monitor position/resolution/orientation/DPI/primary, the source monitor, and per-monitor
effect. [Source: docs/stories/epic-10-layout-simulator.md:107-115, 161-172]
- `MonitorInfo` (`src/Engine/Models/MonitorInfo.cs:8-25`) carries `Id, Name, X, Y, Width, Height,
  IsPrimary` (virtual-desktop device pixels) and a `[JsonIgnore]` `HMonitor`. There is **no rotation
  field and no DPI field** — so:
  - **Orientation** = `Width < Height` (portrait). The editor's orientation toggle just swaps W/H; do
    not add a rotation enum unless a specific test needs it (the epic says the same:
    [Source: docs/stories/epic-10-layout-simulator.md:79-81]).
  - **DPI/scale** is not a `MonitorInfo` field. Carry it in the *scenario fixture* (a per-monitor
    `scale`) and apply it by computing the effective virtual-desktop pixel bounds the same way Windows
    does — i.e. the editor lets you express "this is a 4K panel at 150%" and the fixture resolves to the
    device-pixel rect the engine sees. Document this as an approximation (real per-monitor-V2 DPI is not
    reproduced — see Known fidelity limitations).

### Reproducing SIM_MONITORS exactly
The `SIM_MONITORS` library entry must match `web/src/shared/simulator.ts:33-37` verbatim:
- `\\.\DISPLAY1` "Primary 1440p (sim)" — 2560×1440 @ (0,0), `isPrimary: true`
- `\\.\DISPLAY2` "Right 1080p (sim)" — 1920×1080 @ (2560,180), not primary
- `\\.\DISPLAY3` "Top 1080p (sim)" — 1920×1080 @ (320,-1080), not primary

This is the cross-check that the C# fixture and the long-standing browser simulator agree.
[Source: web/src/shared/simulator.ts:33-37]

### "Simulate display change" → the real re-sync path
The button applies the staged topology to `SimulatedMonitorDetectionService` (10.1) and fires its
on-demand `MonitorsChanged`. The real coordinator handles it unmodified:
- `OnMonitorsChanged` (`src/Engine/Services/EngineCoordinator.cs:1108`) marshals to the UI dispatcher;
- `HandleMonitorsChangedOnUi` (`:1119`) re-reads `GetMonitors()`, pushes the monitors payload, and — if
  enabled — re-syncs effect windows (`SyncEffectWindowsSafeAsync(BuildSpecs())`, `:1140`) and re-pushes
  window configs (`PushWindowConfigs()`, `:1141`);
- removing the source monitor hits the source-lost branch (`:1130-1136`) that disables and toasts.
That is exactly hot-plug / unplug / resolution / orientation coverage with the effect running.
[Source: src/Engine/Services/EngineCoordinator.cs:1108-1145]
- The on-demand fire is the simulator analog of the real impl's debounced
  `SystemEvents.DisplaySettingsChanged` (the production `IMonitorDetectionService`,
  `src/Engine/Services/IMonitorDetectionService.cs:9-19`); the simulator skips the OS event and the
  500 ms debounce so the button is immediate.

### How the engine consumes the topology (don't touch this code)
`BuildWindowConfigFor` (`src/Engine/Services/EngineCoordinator.cs:353`) builds the per-monitor
`WindowConfigPayload` (monitor rect, source rect, relation) from the current monitor snapshots;
`BuildSpecs` (`:324`) enumerates targets; `ResolveSource` (`:320`) picks the source; `PushWindowConfigs`
(`:975`) re-pushes to every open effect window. The editor changes the *inputs* to these; the methods
themselves are unmodified. This is the data the curated library is implicitly testing across layouts.
[Source: src/Engine/Services/EngineCoordinator.cs:320-353, 975-1006]

### Headless render hook — determinism strategy
The hook is the seam a future CI snapshot suite would diff; this story only proves one scenario renders
deterministically. [Source: docs/stories/epic-10-layout-simulator.md:170-172, 194]
- **Fixed pattern, fixed frame index.** The browser `makeSimFrame(elapsedMs, zonesPerEdge, audioBands)`
  (`web/src/shared/simulator.ts:96-129`) is purely a function of `elapsedMs` (hue rotates with
  `ts = elapsedMs/1000`, 124 bpm beat at `:107`). Drive the C# synthetic source (10.1's
  `SimulatedScreenCaptureService`) with a **pinned** `elapsedMs` / frame index and a fixed seed instead
  of wall-clock time, so the same scenario yields the same pixels every run. Pin `maxFps` and
  `zonesPerEdge`/`audioBands` from the fixture.
- **Capture surface.** Reuse the 10.2 composite (or per-surface) output; write PNG(s) to an output dir.
  Determinism is asserted by re-running and comparing bytes / a stable hash (avoid lossy/encoder-nondeterministic
  formats; if WebView2 GPU readback introduces driver-dependent noise, capture per-surface bitmaps or
  the simulated frame buffers rather than the GPU-composited window — note the chosen approach in the
  Dev Agent Record).
- **Out of scope:** the full golden-image diff suite, baseline management, and CI wiring
  ([Source: docs/stories/epic-10-layout-simulator.md:194]). Build only the hook + the single deterministic test.

### Gating & shipping (unchanged from 10.1)
All editor/library/hook code and its UI entry sit behind `#if SIMULATOR_ENABLED` (defined only in the
Debug configuration's `DefineConstants`) plus the runtime `--simulator` arg /
`AMBIENTFX_SIMULATOR` env gate from 10.1. The `--simulator-render` sub-mode is parsed the same way the
existing `--minimized` arg is in `App.OnStartup` (`src/Engine/App.xaml.cs:67`). The Release publish in
`build.ps1` (`dotnet publish ... -c Release`, `build.ps1:78-82`) strips Debug-only constants, so no
simulator IL ships and there is zero Free/Premium/licensing/packaging impact.
[Source: src/Engine/App.xaml.cs:67; build.ps1:76-82; docs/stories/epic-10-layout-simulator.md:90-92, 176-178]
- The csproj (`src/Engine/AmbientFx.csproj`) has no per-config `DefineConstants` today; add
  `SIMULATOR_ENABLED` to a Debug-only `<PropertyGroup Condition="'$(Configuration)'=='Debug'">` (do not
  add it unconditionally — Release must not see it).

### Testing
- **xUnit is the workhorse** for the C#-side fixtures and the hook (no hardware, no WebView2 GPU
  dependency where avoidable):
  - Fixture load/validate: every curated scenario parses against the 10.1 schema; invariants hold
    (exactly one primary, unique ids, positive width/height/scale). Cross-reference the relation
    expectations against `tests/Engine.Tests/Signal/MonitorLayoutTests.cs` (e.g. the 2560×1440-source +
    flush-right 1920×1080 neighbor at (…,180) resolves "right" — see
    `ComputeRelation_MixedResolutionNeighbor_NormalizesByAverageExtent`,
    `tests/Engine.Tests/Signal/MonitorLayoutTests.cs:130-138`) so the library and the projection agree.
  - Save→load round-trip: serialize an authored topology, reload, assert field-equality across all AC1
    fields.
  - Headless determinism: run the hook twice for one scenario with the fixed seed/frame index; assert
    byte-equal artifact (or equal content hash). Keep this test off any real-hardware / real-WGC path.
- **Vitest**: no bridge-contract change is expected (AC7), so web tests should need no new coverage; if
  the editor reuses any existing web control surface, keep its tests green. Mirror any payload change in
  `src/Engine/Bridge/` only if one is unavoidable (it should not be).
- **Manual (dev/QA):** load each curated scenario, drag/resize/rotate, hit "simulate display change" for
  each of the four change kinds, save and reload a custom layout. The simulator does not replace owner
  verification on real extra monitors (see below).

### Out of scope
- **Full CI golden-image regression suite** — only the headless render hook + one deterministic-artifact
  test are in scope. [Source: docs/stories/epic-10-layout-simulator.md:170-172, 194]
- **Real-hardware capture/placement fidelity** — synthetic/media frames bypass WGC; viewports
  *approximate* OS window placement and per-monitor-V2 DPI; only the 10.3 "mirror" source exercises real
  capture. This tool is not a substitute for owner verification on real extra monitors.
  [Source: docs/stories/epic-10-layout-simulator.md:188-191]
- **Indirect Display Driver (IDD) path** — remains the documented future option for true OS-level
  extra-monitor fidelity; not built here. [Source: docs/stories/epic-10-layout-simulator.md:24-29, 192-193]
- **New rotation/DPI fields on `MonitorInfo`** — orientation is `width<height`; DPI/scale lives in the
  fixture. Don't change the model unless a test forces it.
- **Retrofitting the production UI** — the editor is dev-only; no Free/Premium UI changes.
