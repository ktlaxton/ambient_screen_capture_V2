# Story 8.3: Additional Vendors & Audio-Reactive Peripherals

## Status
Done — implemented, tested, and owner-verified 2026-06-12 (audio-reactive on Corsair
hardware; the multi-vendor half of AC8 stays open until non-Corsair gear is available).

## Depends on
8.1 (vendor-neutral device service + projection). Pairs well after 8.2 (per-device placement) but
does not strictly require it.

## Story
**As a** user with a mixed RGB setup (not all Corsair) who likes the screen's audio reactivity,
**I want** my non-Corsair peripherals to join the ambient lighting and, optionally, pulse with the
audio,
**so that** the whole desk reacts together — every brand of hardware and the beat of what I'm
playing.

## Context
Story 8.1 deliberately shipped Corsair-only but built the device sink **vendor-neutral** on top of
RGB.NET, which already supports Razer, Logitech, ASUS, MSI, SteelSeries and more through separate
device providers. This story turns those on and verifies them, and adds an optional audio-reactive
peripheral mode that reuses the audio data already in every frame (`FramePayload.Audio` —
`Intensity` + per-band `Bands`), which today only the on-screen effects consume.

## Acceptance Criteria
1. **Additional providers selectable.** At least one non-Corsair RGB.NET provider (e.g. Logitech or
   Razer — owner's available hardware decides) is enabled, discovered, position-mapped, and driven
   through the **same** `IAmbientDeviceService` pipeline as Corsair — no per-vendor branching in the
   mapping/output code.
2. **Provider availability is graceful.** Each provider that isn't installed/available is skipped
   cleanly (its absence is a normal state, never an error); the device list shows only what's
   actually present. Multiple providers can be active at once (Corsair + another) without conflict.
3. **Provider enable/disable in the UI.** The user can turn individual vendor providers on/off (some
   users won't want the app touching a given ecosystem). Defaults are sensible (Corsair on; others
   off until enabled, to avoid surprises and reduce startup cost).
4. **Audio-reactive peripheral mode (optional).** A toggle adds an audio-reactive layer to the
   peripheral output, driven by `FramePayload.Audio` — e.g. overall `Intensity` modulates peripheral
   brightness and/or `Bands` drives a spectrum across a strip. It composes with the position-mapped
   color (a modulation on top, not a replacement) and has at least a depth/strength control.
5. **Performance holds with multiple providers.** The ~30 Hz rate-limited update budget from 8.1 is
   respected across all active providers combined; adding vendors/audio does not flood hardware or
   regress host responsiveness.
6. **Persistence + bridge.** Provider enable flags and the audio-reactive settings persist via
   `ApplicationSettings`, mirror in `bridge.ts`, apply live, and are back-compatible.
7. **Tests green & extended.** xUnit covers the audio-modulation math (pure: given intensity/bands +
   base colors → modulated colors) and multi-provider service lifecycle with mocked providers.
   Vitest covers the provider toggles and audio-reactive controls. Existing suites stay green.
8. **Real-hardware verification.** Owner-verified on at least one non-Corsair device alongside
   Corsair, and the audio-reactive mode visibly responding to playback. (Recorded in QA Results.)

## Dev Notes

### The audio data is already in every frame
[Source: `src/Engine/Bridge/EngineMessages.cs:48-55` (`AudioData { Intensity, Bands }`)]
- `FramePayload.Audio` carries overall `Intensity` (0..1) and normalized per-band `Bands` (low→high),
  the same data the on-screen effects (e.g. audio-bars, edge-glow's pulse) already use. The
  peripheral audio mode is a new consumer of it — no new audio capture/analysis. Keep the modulation
  a **pure helper** so it's unit-tested without hardware (mirrors the project's
  `MonitorLayout`/projection testing discipline).

### Vendor-neutral pipeline must not leak vendor branches
[Source: Story 8.1 `IAmbientDeviceService`]
- 8.1's abstraction was built so adding a provider is registration-only. If this story needs
  per-vendor special-casing in the mapping/output code, that's a smell — push the difference behind
  the provider/device abstraction instead.

### Defaults and trust
- Don't light up every ecosystem on first run — users may not want the app touching their Razer/
  Logitech config. Corsair on (the epic's primary target), others opt-in. Document the startup cost
  of each provider (some scan slowly).

### RGB.NET provider notes (confirm during implementation)
- Each vendor provider has its own availability/SDK requirement (e.g. Logitech LGS/G HUB, Razer
  Synapse/Chroma SDK). Treat each like iCUE in 8.1: required-and-running for that vendor, absent =
  skipped. Verify the exact "is available" probe per provider.

### Scope
- This story adds **vendors + audio reactivity**, not placement UI (8.2) or installer/licensing
  hardening (8.4). Which specific non-Corsair vendor ships first depends on the owner's hardware —
  pick what can actually be verified (AC8).

### Testing
- xUnit for audio-modulation + multi-provider lifecycle (mocked, no hardware). Vitest for UI.
- Owner manual pass for a real non-Corsair device + audio response (AC8).

### Completion Notes List
- **All six vendors enabled at once, not one:** the story says the owner's hardware decides
  which non-Corsair vendor ships first, but the hardware inventory isn't known at dev time —
  so every major RGB.NET provider (Logitech, Razer, ASUS, MSI, SteelSeries, Wooting) is in
  the registry as an opt-in toggle, each independently skip-if-absent. AC8 can be verified
  against whatever non-Corsair gear is actually on the desk; if none exists, AC8 should be
  recorded as not-applicable until hardware is available.
- **Vendor natives are NOT bundled** (unlike the Corsair iCUE SDK dll from 8.1): Razer/
  Logitech/ASUS/MSI/Wooting need their vendor software or SDK natives present on the system;
  if missing, the provider simply reports "not found". Bundling decisions belong to the 8.4
  installer/licensing review.
- **`SubmitFrame` contract changed** from `EdgeColors` to the whole `FramePayload` so the
  service sees `Audio` — the audio layer is one brightness factor per frame
  (`AudioModulation.BrightnessFactor`), multiplied into the existing effective-brightness
  chain (global × per-device × audio), so it composes with 8.2 placement and costs no extra
  hardware pushes.
- **Provider set changes force a reconnect** (Stop → Start with the new set) because RGB.NET
  providers attach at session start; placements/brightness/audio stay live-apply.
- The overall connection state is now summarized from per-provider outcomes
  (`RgbProviderStates.SummarizeNoDevices`, pure + unit-tested): any refused → refused, all
  absent → icueNotFound (shown generically), etc. The per-provider chips in the UI carry the
  vendor-specific detail.
